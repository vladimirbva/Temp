## О ПРОЕКТЕ (читай обязательно)

**Yaseek** — PWA-трекер кормления младенца. Один пользователь-семья (мама/папа, до 2 взрослых
+ до 2 детей). Стек: ASP.NET Core (.NET 10), SQLite (EF Core), клиент — vanilla JS без сборщиков
и фреймворков (один файл wwwroot/app.js ~380 КБ, модалки через `<dialog>`, тосты, офлайн-очередь
в localStorage), Service Worker (wwwroot/sw.js), графики — Chart.js (уже в проекте).

### Структура проекта
- `src/Yaseek.Api/Program.cs` — точка входа, версии (`AppBuild.Current`), подключение эндпоинтов.
- `src/Yaseek.Api/Program.Ep.*.cs` — эндпоинты по зонам (Feeds, Stock, Chat, Journal: сон/стул/замеры/болезни/прививки/лекарства, Push, Admin, Doctor, Reports, Export).
- `src/Yaseek.Api/AppDb.cs` — EF Core DbContext + records DTO + миграции схемы (SchemaVersion 1..12, поле в таблице Meta).
- `src/Yaseek.Api/HungerModel.cs` — модель голода: прогноз следующего кормления. Параметры в таблице HungerState: Mu (средний интервал в ч), Circ[1..4] (множители по локальным часам: 0-6 ночь, 6-12 утро, 12-18 день, 18-24 вечер), Sigma (внутренняя σ), TotalN. Наружная σ = внутренняя × 1.36 (константа SigmaCalib, v15.12).
- `src/Yaseek.Api/HungerScheduler.cs` — Runner: прогноз, статусы (green/yellow/red), «скоро кормить» (SoonPush ≤30 мин), потолок push (PushDailyCap=8: «жёлтый»+«скоро» на ребёнка за локальные сутки; красный всегда идёт; счётчик SettingsStore «pushCap.<kidId>» = "<ISO-дата>|<n>", сброс в 00:00 по tz). Эскалация жёлтого в красный (≥90 мин) — EscalateYellowToRed (v15.10).
- `src/Yaseek.Api/Metabolism.cs` — устаревшие веса (48 строк, таблица MetabolismWeights — ИСТОРИЯ, живым кодом не читается, НЕ ТРОГАТЬ).
- `src/Yaseek.Api/wwwroot/app.js` — весь клиент. `index.html` (23 `<dialog>`), `styles.css`, `sw.js` (CACHE 'yaseek-v130').
- Тесты: `src/Yaseek.Tests/` — xunit, 192 теста, ЗЕЛЁНЫЕ на момент передачи. Нумерация миграций: следующий шаг — 13 (если нужна).

## ШАГ: «Самообучение» (v15.15)

### Цель
Модель калибруется по реальному журналу сама (без ручной пересборки), прогнозы оцениваются
по факту, владелец видит «сколько реально помогает».

### Требования

**R1. Пересборка параметров (сервер).**
- Новый сервис `LearnService` (файл `src/Yaseek.Api/LearnService.cs`): метод Rebuild(KidId, db)
  пересчитывает из журнала кормлений последних 60 дней: Mu (EWMA-среднее интервалов с паузами
  >24 ч — РЕАЛИЗАЦИЯ уже есть в движке/бэктесте — реюзни существующий код, не дублируй логику),
  Circ (средние интервалы по 4 buckets локальных часов, минимум 5 кормлений на bucket, иначе
  bucket = 1.0), Sigma (σ остатков интервалов, клампы как в движке).
- Триггер: при вызове /api/sync — если прошло ≥24 ч с последнего пересчёта И появилось ≥3 новых
  кормлений. Прошлый пересчёт — поле SettingsStore "learn.<kidId>" = "<ISO-UTC timestamp>".
- После пересчёта логировать (serilog-консоль, как принято в проекте): «learn: rebuilt kid N:
  mu=X, sigma=Y, circ=[...]». Не пересчитывать чаще 1 раза в 24 ч на ребёнка.
- Пересчёт НЕ должен ломать активные состояния: если в момент пересчёта идёт красный статус —
  пересчёт отложить (не менять state до завершения текущего интервала).

**R2. Лог прогнозов (миграция 13).**
- Таблица `PredictionsLog`: Id, KidId, CreatedAtUtc, AtLocalHour (int), P (double), MuAt (double),
  SigmaAt (double), Status (green/yellow/red), FedAtUtc (null — прогноз ещё не «закрылся»),
  WasAccurate (null/true/false).
- Запись создаётся при смене статуса прогноза (не чаще 1 раза в час на ребёнка), закрывается
  следующим кормлением: WasAccurate = |факт − прогноз| ≤ 30 мин.
- Миграция 13: CREATE TABLE + индекс (KidId, CreatedAtUtc). Все NOT NULL с дефолтами.
- Старые данные не мигрируются (таблица пустая — это норм).

**R3. Счётчик «прогноз сбылся» (клиент).**
- На вкладке «Статистика» новый блок: «Точность прогнозов»: за последние 30 дней: % сбылся
  (±30 мин), всего прогнозов, MAE (среднее |ошибка| в мин). Данные: новый эндпоинт
  GET /api/learn/accuracy?kidId=N — агрегаты по PredictionsLog.
- Если данных <10 прогнозов — блок показывает «мало данных — учимся».

**R4. Еженедельный дайджест push.**
- PushService: раз в неделю (первая синхронизация после понедельника 10:00 локального времени)
  — push-сообщение: «Неделя Яна: средний интервал 3.2 ч, ритм сместился: утро −12 мин»
  (текст собирается из дельт Circ текущей недели против предыдущей; без паники, сухие факты).
- Гейт: SettingsStore "digest.<kidId>" = "<ISO-недели>"; если не прошло 7 суток — молчание.
- Push не отправляется, если у пользователя нет push-подписки (как принято в PushService).

### Приёмка (проверь сам перед сдачей)
1. Полный тест-пакет зелёный (192 + новые).
2. Новый: Rebuild на синтетике из 10 кормлений даёт mu в разумных границах; повторный вызов
   через 1 час — ничего не делает; PredictionsLog закрывается корректно.
3. Смоук: /health ok, /api/version 15.15, блок «Точность прогнозов» на пустой таблице — «мало
   данных», миграция v12→v13 идёт без потери данных (существующий тест-паттерн миграций).
4. Дайджест: локальное время недели соблюдается; второй вызов в ту же неделю — молчание.

- Не трогать формулы движка (README!). Пересборка только заполняет существующие поля state.
