### 1. Критические баги в коде (Code Bugs)

**🔴 Баг №1: Инверсия знака в «расходы:» vs «условия:/арм.» (Фатально для М1)**
*Суть:* В журнале строка `расходы:` печатает `Fc_r*(e27-1)`, где множитель ≈ `-1`. Знак инвертируется. В `Model.cs` словарь `NodeSnapshot.Flows` сохраняет это значение «как есть».
*Проблема:* Метод М1 (Зеркальная асимметрия) берет значения из `Flows` и сравнивает их с `CondRec.Value` (где `+` = приток) или `Armature.F`. Из-за того, что парсер не домножил `Flows` на `-1`, М1 увидит `10` в условиях и `-10` в расходах для **одной и той же связи** и выдаст фантомное расхождение (Balanced Defect).
*Решение:* В `Parsers.cs` при разборе строки «расходы:» явно инвертировать знак: `flow = -parsed_value;`. В модели данных `Flows` должен храниться **нормализованный физический знак** (+ приток к владельцу карточки), совпадающий с `Conds` и `Arms`.

**🔴 Баг №2: Ложная логика в `NodeRecord.ValveAlways()`**
```csharp
public bool ValveAlways(string valve) {
    bool seen = false;
    foreach (var s in Snaps) 
        foreach (var a in s.Arms) 
            foreach (var v in a.Valves)
                if (v.Valve == valve) { seen = true; if (v.Value < 0.5) return false; }
    return seen;
}
```
*Проблема:* Если клапан отсутствует в сканах 1, 2, 3, но появляется в скане 4 с `Value=1.0`, метод вернет `true`. Это нарушает контракт "открыт во **всех** сканах".
*Решение:* Проверять наличие клапана в *каждом* снимке. Если в каком-то скане клапана нет в списке `Arms` — немедленно `return false`.

**🟡 Баг №3: Ошибка индексации в `LogBuilder` (Самотесты)**
В `SelfTestRunner.cs` (метод `NodeCard`):
```csharp
int i = 1;
foreach (var c in conds) condTxt.Append($"U{i}({c.link,3})={Num.F(c.u, 2)} <{Num.F(c.ls, 1)}%>/ ");
i++; // <-- Инкремент ВНУТРИ цикла!
```
*Проблема:* Переменная `i` всегда равна 1 для всех условий (генерируется `U1(2)... U1(3)...`). То же самое с `links`. Если парсер в `Parsers.cs` строгий и ожидает `U1, U2, U3`, синтетические тесты с множественными связями будут падать или перезаписывать друг друга в модели данных. Инкремент нужно перенести внутрь `foreach` или использовать `Select((c, index) => new { c, index })`.

**🟡 Баг №4: `Num.Median` не соответствует комментарию**
Комментарий гласит: *"Медиана без выбросов (устойчивая статистика для плато)"*. Но код делает обычный `Sort()` и берет центральный элемент.
*Проблема:* Обычная медиана устойчива к одиночным выбросам, но если «плато» состоит из четного числа точек, где половина — мусор (например, из-за kerr), медиана может сдвинуться. Для детектора плато (τ) лучше использовать **Trimmed Median** (отбрасывать 10% верхних и нижних значений перед сортировкой).

### 2. Физические и методологические ошибки (по вашим замечаниям ZM.txt)

**1. Признаки М12 (Мёртвые блоки)**
*Ваши слова:* «В руководстве — условия связи = 0 при открытой арматуре, а в коде — счётчик условий никогда не >2».
*Вердикт:* Это подмена понятий. М12 должен искать **топологический тупик**: `cond.Value == 0` И `arm.AnyOpen == true` (или `K > 0.5`) И `Fc == 0`. Признак «счётчик никогда не >2» — это артефакт затирки памяти (XX0[7]), который должен быть вынесен в отдельный метод (например, **М17: Дефекты памяти/счетчиков**), а не подмешан в физику М12.

**2. «У И:» печатается дважды**
*Вердикт:* В `Model.cs` класс `ScanInfo` имеет `HasHealth` (bool), а `HealthPoint` хранится в `LogSession.HealthUi` (List). Если в логе две строки `У И:` за один скан (например, для двух разных БУИ), парсер должен не перезаписывать, а добавлять в список с привязкой к `Scan` и `WallMs`. В самотестах это не покрыто.

**3. Паспорт: Бейдж «Безопасный режим»**
Сейчас `RunPassport.IsNumeric` возвращает `false`, если паспорт не подтвержден, и методы блокируются. Но UI не сообщает об этом явно.
*Требование:* Если `OperatorConfirmed == false`, на экране «Обзор» и в шапке КТК-документа должен гореть **красный бейдж "SAFE MODE (Structure Only)"**. Иначе аудит клиент (Газпром ВНИИГАЗ) не примет отчёт.

**4. Карточка узла: 9 строк, а не 8**
В комментариях к `NodeSnapshot` написано `// 8 строк дампа`. Но по факту kerr от -200 до -208 — это 9 строк (или 10, если считать `осн:`). Нужно поправить парсер (машину состояний в `Normalizer.cs`), чтобы он не обрывал карточку, если встречает 9-ю строку `Для OI (OI|TUBE)`.

### 3. Предложения по повышению удобства (UX) и функционала

Чтобы приложение перешло из разряда «анализатор текста» в полноценный «инженерный инструмент», предлагаю внедрить следующие фичи:

#### А. Политика кодировки и Troubleshooting (Обязательно для релиза)
*   **Encoding Fallback:** В `Normalizer.ParseFile` сделать жесткую логику: `UTF-8 -> CP1251 -> KOI8-R`. Если эвристика сомневается (например, валидный CP1251 декодируется как мусор), писать в `RunPassport` поле `EncodingWarning = "Auto-detected CP1251, verify if charts are broken"`.
*   **Экран Troubleshooting:** Добавить в UI раздел «Помощь», где описано:
    *   *Лог не читается / бинарный мусор:* Проверить, не открыт ли файл в другой программе, проверить кодировку.
    *   *Огромный файл (>500 МБ):* Использовать `--selftest` без UI или включить децимацию в настройках.
    *   *Модули перепутались:* Инструкция по ручному маппингу `KitName -> Module`.

#### Б. Сценарий «Эталонный прогон» (Reference Run)
Сейчас `Comparison.cs` сравнивает два открытых лога. Нужно добавить функционал **эталона**:
1.  Кнопка «Сделать эталоном» на экране «Сравнение».
2.  Приложение сохраняет текущий `ConvergenceReport` и `Findings` в файл `KtkData/reference_run.json`.
3.  При следующей загрузке лога (например, после фикса кода модели) приложение **автоматически** строит дельта-график `Current vs Reference`.
4.  Если время сходимости (τ) выросло более чем на 10% или появилось >5 новых `Fail` находок — система генерирует **Алерт регрессии**.

#### В. Известные дефекты печати (CG4 / GROFF)
В `Methods2.cs` (М6) нужно добавить фильтр `KnownDefects`. Если парсер видит в логе `GROFF=0` или `GR_rep` без сброса, М6 **не должен** генерировать `Finding` с `Severity.Fail`. Он должен создавать `EventKind.Info` с текстом: *"Замечен известный дефект печати CG4 (не влияет на физику, игнорируется при расчёте баланса)"*. Это спасет нервы операторам.

#### Г. Экспорт «Пакета клише» (Traceability Package)
КТК-документ (HTML) хорош для чтения, но плох для аудита. При экспорте КТК генерировать **ZIP-архив**, содержащий:
1.  `ktc_report.html` (сам документ).
2.  `run_passport.json` (снимок настроек и констант).
3.  `selftest_report.txt` (доказательство, что ядро валидно).
4.  `suspicious_scans.csv` (выгрузка сырых строк лога, на которых сработали М1-М16, для ручной проверки).
