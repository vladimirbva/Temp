ЧАСТЬ I. СУТЬ, КОНЦЕПЦИЯ, ЧЕСТНЫЙ ВЫБОР ТЕХНОЛОГИИ, БЮДЖЕТ

1. ЧТО СТРОИМ
--------------------------------------------------------------------------------
[ОБЯЗ] Встроенный офлайн-ассистент с именем «Владимир 26» — чат-экран внутри
КТК-Анализатора, который:
  1) рассуждает о находках М1–М25: объясняет по обязательной схеме
     СИМПТОМ → СВИДЕТЕЛЬСТВА → ГИПОТЕЗЫ (ранжированы, с весами) →
     ЛОКАЛИЗАЦИЯ (юнит → kerr-блок → строка) → ПРОВЕРКА → УВЕРЕННОСТЬ;
  2) локализует ошибки до юнита/блока/строки (на активах слоя 0.5 и KerrRegistry);
  3) говорит синтезированной речью «от корня»: ответы собираются из лемм,
     грамматических каркасов и живых метрик приложения — НЕ выбираются из списка
     зашитых фраз (контракт анти-шаблона, раздел II);
  4) отвечает на посторонние вопросы («как дела», «как тебя зовут», общие темы —
     спорт, история, кулинария…) из курируемого 10%-среза знаний;
  5) сам задаёт вопросы оператору (пытливость) и ОБРАБАТЫВАЕТ его ответы:
     «да/нет» на диагностический вопрос байесовски двигает веса гипотез и
     сужает локализацию ошибки; ответы заполняют паспорт прогона и профиль;
  6) умеет располагать к себе: обращение по имени, память между сессиями,
     эмпатия по маркерам, форма «ты/вы».
[ОБЯЗ] Синтез речи — это синтез ТЕКСТА из пропозиций. TTS-аудио (озвучка) в
базовую поставку НЕ входит (см. XVI — [ТВОРЧ] отдельным ТЗ, если понадобится).

2. ЧЕСТНЫЙ ВЫБОР ТЕХНОЛОГИИ: СИМВОЛИЧЕСКИЙ АССИСТЕНТ, НЕ LLM
--------------------------------------------------------------------------------
[ОБЯЗ] Генеративная LLM размером 20–50 МБ не существует; малые модели даже в
4-битной квантизации — 90–400+ МБ, с галлюцинациями, недопустимыми для аудита
ВНИИГАЗ. Принятый путь — символический ассистент: морфологический синтезатор +
база знаний + детерминированный диагностический reasoner.

| Критерий                 | Символический (принято)     | Локальная LLM       |
|--------------------------|-----------------------------|---------------------|
| Размер базы              | 8–15 МБ, поставка ≤50 МБ    | 90–400+ МБ          |
| Галлюцинации             | Невозможны по контракту     | Неустранимы         |
| Детерминизм (аудит)      | 1 вопрос + 1 сессия =       | Нет                 |
|                          | байт-в-байт один ответ      |                     |
| Локализация ошибок       | Прямая: kerr→блок→файл:стр. | «Плавающая»         |
| Свободный small talk     | Ограничен, но композиционен | Хороший             |
| Скорость ответа          | <150 мс                     | 1–10 с на CPU       |

[ТВОРЧ] Опциональный локальный SLM-плагин (300–500 МБ, отдельная загрузка,
выключен по умолчанию): LLM формулирует, символический Realizer остаётся
контролёром фактов (проверка чисел/имён в выходе). В базовую поставку НЕ входит.

4. КОНТРАКТ АНТИ-ГАЛЛЮЦИНАЦИЙ («атомы»)
--------------------------------------------------------------------------------
[ОБЯЗ] Realizer принимает числа, имена узлов/связей/арматур, kerr-коды и даты
как АТОМЫ — он умеет их обрамлять и склонять окружающие слова, но НЕ умеет их
порождать. Ни одно число и ни один идентификатор в ответе не может появиться,
если его нет в: (а) модели Core, (б) KB, (в) живых метриках приложения, (г)
реплике самого оператора.
[ОБЯЗ] Ассистент НЕ читает Finding.Message (готовые строки) — он берёт
СВИДЕТЕЛЬСТВА (числа, сканы, имена, kerr) из полей находки и модели и строит
объяснение заново через Planner→Realizer. Иначе получится пересказ зашитых фраз.
[ОБЯЗ] Для незнакомого факта (вопрос вне KB) — честный каркас UNKNOWN_HONEST:
«не знаю» + предложение занести в очередь дообучения. Выдуманный факт =
нарушение приёмки (B14).

5. КОНТРАКТ АНТИ-ШАБЛОНА («ни одной зашитой фразы»)
--------------------------------------------------------------------------------
[ОБЯЗ] В коде папки Assistant/ запрещены литеральные полные русские предложения
длиннее 3 слов. Разрешены: леммы, атомы, имена объектов, служебные ключи,
короткие коннекторы (≤3 слов: «поэтому», «из-за этого», «как дела» — только как
КЛЮЧИ каркасов, не как готовые ответы).
[ОБЯЗ] Приёмочная проверка A23: автоматический скан исходников Assistant/ на
русские литералы ≥4 слов — 0 вхождений (исключение: строки-эталоны тестов в
SelfTest, помеченные маркером // SPECH-TEST).
[ОБЯЗ] Комбинаторика: стартовый набор 40 каркасов (раздел V) + ~60
вопросительных/small talk каркасов (Э5); целевой объём к v3.1 — ~200 каркасов.
Один и тот же факт в разных контекстах звучит по-разному (синонимы связок,
порядок слов, местоимения), но детерминированно.

6. КОНТРАКТ ДЕТЕРМИНИЗМА (аудит ВНИИГАЗ)
--------------------------------------------------------------------------------
[ОБЯЗ] seed вариативности = hash(MessagePlan + стиль-настройки + идентификатор
сессии). Повторный вопрос в той же сессии → байт-в-байт идентичный ответ.
[ОБЯЗ] Версия KB (sha256) и версия каркасов пишутся в паспорт КТК и в журнал
диалога — аудит проверяет, какой базой отвечал ассистент.

7. КОНТРАКТ ОФЛАЙННОСТИ И РАЗГРАНИЧЕНИЯ ПРАВ
--------------------------------------------------------------------------------
[ОБЯЗ] Ни одного сетевого вызова (проверка A20/B11: приёмка с отключённой
сетью). Никаких внешних сервисов, обновлений, «проверок лицензий».
[ОБЯЗ] Ассистент МОЖЕТ: читать модель журнала, находки, паспорт, юниты, KB,

[ОБЯЗ] Ассистент МОЖЕТ писать ТОЛЬКО: паспорт прогона (каждое поле — с явным
подтверждением оператора: «Подтверждаете?» и только после «да» —
OperatorConfirmed), профиль оператора, веса фидбэка, журнал диалога.
[ОБЯЗ] Ассистенту ЗАПРЕЩЕНО без отдельного подтверждения владельца:

12. ФОРМАТ СЛОВАРЯ morph.dict
--------------------------------------------------------------------------------
[ОБЯЗ] TSV: lemma \t POS \t paradigm \t gender \t anim [\t flags]. Парадигмы —
номера по Зализняку (или собственные коды при конвертации дампа). Минимальный
набор собственных доменных парадигм (перечень обязателен):
  существительные: F_a (находка/книга), M_hard (стол/узел), F_soft_3rd (связь —
  3-е скл., на-ь), N_o (окно/давление), M_soft (рубль), pluralia (сутки);
  прилагательные: adj_hard (закрытый), adj_soft (синий), adj_stressed (новый);
  краткие причастия/прилагательные: part_closed (закрыт/закрыта/закрыто/закрыты);
  глаголы: V_at1 (печатать — I спр.), V_it2 (строить — II спр.), V_ет2 (тратить),
  V_irregular (путь/хотеть/дать — полный список форм в исключениях);
  наречия/предлоги/союзы: неизменяемые, без парадигм.
[ОБЯЗ] Исключения (_irregular): путь/время/дочь/перо + все глаголы с чередованиями
и супплетивизмом — 2–3 тыс. полных форм из дампа; допускаются частичные.
[ОБЯЗ] Беглые гласные Р.п. мн. (находок, окон, писем) — флагом парадигмы («+о»
и аналоги); одушевлённость — В.п. = Р.п.
[ОБЯЗ] Честный fallback: неизвестная лемма НЕ склоняется (возвращается как
есть) и попадает в очередь «Не понял — дообучи?» — НЕ ломать ответ.
[ОБЯЗ] Морфосинтез = stem + окончание парадигмы. Краткая форма причастия:
«закрытый → закрыт/закрыта/закрыто/закрыты» — техречь предпочитает краткие.

13. ЧИСЛИТЕЛЬНЫЕ И СОГЛАСОВАНИЕ (обязательные правила)
--------------------------------------------------------------------------------
[ОБЯЗ] Counted(N, lemma): 1 находка / 2 находки / 5 находок / 11–14 находок /
21 находку / 112 находок (11–14 — Gen.Pl всегда; %10 == 1 → Nom.Sg; 2–4 →
Gen.Sg; иначе Gen.Pl).
[ОБЯЗ] Словесные числительные («девятнадцать» → 19) — при разборе ответов
оператора (AnswerIntake): таблица 0–100 + «полторы/двое/трое» (паспорт).
[ОБЯЗ] Валентности глаголов хранятся в каркасах: «равен → Dat», «проверить →
Acc», «свидетельствовать о → Pre», «указывать на → Acc», «привести к → Dat»,
«интересоваться → Ins». Падеж объекта вычисляется в рантайме — один каркас
порождает «проверить блок / проверку проводимости / эти связи».

14. ОБРАТНАЯ ЛЕММАТИЗАЦИЯ (для NLU)
--------------------------------------------------------------------------------
[ОБЯЗ] Lemmatize(текст): токенизация → для каждого токена перебор парадигм
«в обратную сторону» (прямой индекс поверхность→лемма, строится компилятором из
morph.dict — НЕ наивный перебор в рантайме); для unknown-токенов — эвристики
(конечности -ами/-ах/-ой/-ов) + очередь дообучения. Скорость: журнал запросов ≤
2 мс на реплику.

ЧАСТЬ V. NLG-РЕАЛИЗАТОР: ПРОПОЗИЦИИ → РЕЧЬ (БЕЗ ЗАШИТЫХ ФРАЗ)
================================================================================

15. ПРОПОЗИЦИИ И ПЛАНЫ
--------------------------------------------------------------------------------
[ОБЯЗ] Пропозиция = Clause(verbLemma, subjLemma, objLemma?, ObjCase,
ObjAtom?, FocusObj?, Kind{Declarative, Question}). MessagePlan = список клауз +
отношения между соседними: None / Cause / Contrast / Evidence / Recommend + Seed.
Пример (находка М12 — НИ ОДНОЙ строки-заготовки):
  CLOSED(valve:k136hl) + CAUSE → ZERO_FLOW(edge:151↔212)
  ↓ лексикализация: клапан/закрытый/расход/связь/равный/ноль
  ↓ каркас CAUSE: [Клауза1], поэтому [Клауза2] (варианты: поэтому/следовательно/
    из-за этого — выбор по seed)
  ↓ валентность: «равен» управляет Дат.п. → «нулю»; «закрыт» — краткое,
    согласование с «проводимость» (ж.р. → закрыта)
  ↓ порядок: тема вперёд, рема в конец; фокус=значение → «…равен нулю»
  ↓ референция: первое упоминание «клапан k136hl», повторное «он» (м.р. из
    лексикона)
  Результат: «Клапан k136hl закрыт, поэтому расход в связи 151↔212 равен нулю.»

16. СТАРТОВЫЙ НАБОР 40 КАРКАСОВ (эталон для исполнителя; расширение до ~200)
--------------------------------------------------------------------------------
Диагностические (DIAG, 6):
  D1 SYMPTOM «{obj} {symptom-verb}» (краткое причастие/глагол)
  D2 EVIDENCE «это видно в сканах {atom}: {witness-atom}» (перечисление через
     двоеточие; числа — только атомы)
  D3 HYPOTHESIS_RANK «вероятнее всего {hypo}; не исключено {hypo2}» (веса →
     лингвистическая градация: >0.6 «вероятнее всего», 0.3–0.6 «возможно»,
     <0.3 «маловероятно»)
  D4 LOCATE «область поиска — блок {kerr-range}, процедура {proc}, юнит {file}»
  D5 CHECK «проверьте: {check-предложение из why-дерева}» (Action-кнопка)
  D6 CONFIDENCE «уверенность {grad}: {basis}» (честная: чем меньше данных, тем
     ниже градация — не «100%»)
Связки (4): Cause (поэтому/следовательно/из-за этого), Contrast (но/однако/
при этом), Evidence (это подтверждается/на это указывает), Recommend
(рекомендую/стоит/предлагаю).
Мета (META, 8):
  M1 NAME («меня зовут {atom:имя}» + клауза-тёзка из карточки)
  M2 ROLE («я — {role-lemma}, {версия}»)
  M3 STATE (из живых метрик сессии — см. Персона)
  M4 CAPABILITY (каркас перечисления реестра Tools)
  M5 TIME_GREETING (по системным часам: утро/день/вечер/ночь)
  M6 DATE (атом даты)
  M7 WEATHER_HONEST (честно: сенсоров нет + мост к метрикам прогона)
  M8 HOWARE_YOU_Q (встречный вопрос «а у вас как?»)
Диалоговые (DIALOG, 8):
  K1 ACKNOWLEDGE (доказательство понимания: домен + 2–3 леммы вопроса,
     склонённые через валентности)
  K2 BOUNDARY (вежливая граница RED: «вне моей специализации; близкая тема —
     {bridge}»)
  K3 BRIDGE (мост к проекту из GRAY: ближайшая GREEN-тема из фокуса сессии)
  K4 OFFER («показать?/рассказать подробнее?»)
  K5 CLARIFY (уточнение: не хватает слота → топ-3 кандидата из фокуса)
  K6 RECALL («в прошлый раз вы говорили, что {факт}» — факт склоняется)
  K7 THANKS_ACK («принял/записал/запомнил» — отражение извлечённого факта)
  K8 FOLLOWUP (решение follow-up: продолжить нить или вернуть к проекту)
Вопросительные (Q, 6):
  Q1 OPEN_WHAT / Q2 OPEN_WHY / Q3 OPEN_HOW / Q4 OPEN_HOWMANY (числительное в
     вопросе — через Counted) / Q5 CLOSED_YN / Q6 CHOICE_AB
GRAY-срез (4): G1 FACT_INTRO («{concept} — {pred-пропозиция}»), G2 FACT_PROP,
G3 FACT_ATTR (атрибут с параметром), G4 CURIOSITY_Q (встречный вопрос из
карточки). Small talk (4): S1 GREET_TIME, S2 EMPATHY (по маркерам фрустрации),
S3 PRAISE_FEEDBACK, S4 REFUSAL_POLITE.
[ОБЯЗ] Все каркасы — декларативные структуры в grammar.json (без кода); новые
каркасы добавляются в KB без пересборки приложения (принцип «обучение без
правки кода»).

17. ВАРИАТИВНОСТЬ БЕЗ РАНДОМА
--------------------------------------------------------------------------------
[ОБЯЗ] Синонимические реестры связок и глаголов (поэтому/следовательно/
из-за этого; наблюдается/зафиксировано/виден); выбор по seed плана; чередование

базы И доля карточек ≤10% (обе меры). Фиксируется в отчёте сборки и в паспорте
КТК (поля kbGeneralPctBytes, kbGeneralPctCards). Нарушение — сборка не проходит.
| Срез        | Содержимое                                                | Размер      |
|-------------|-----------------------------------------------------------|-------------|
| Проектный 90% | why-деревья М1–М25, kerr-карта, конвенции, доки, индекс | ~7–13 МБ    |
|             | юнитов, морфословарь домена                              |             |
| Общий 10%   | ~3000 энциклопедических карточек-троек (наука, техника,   | 0.8–1.4 МБ  |

|             | каркасы small talk                                       |             |
| Служебное   | профиль, журнал диалога, веса фидбэка                     | ≤0.3 МБ     |
[ОБЯЗ] Карточка общего среза — ПРОПОЗИЦИИ, а не текст:
  {"concept": "футбол", "lemmas": ["футбол","матч","команда","мяч"],
   "facts": [{"pred":"является","subj":"футбол","obj":"командный вид спорта"},
             {"pred":"длится","subj":"матч","obj_atom":"90 минут"}],
   "curiosity": {"pred":"интересоваться","obj":"футбол","kind":"open"},
   "bridge": null}
Realizer собирает ответ из пропозиций; контракт атомов действует и на срез.
[ОБЯЗ] Источники среза — офлайн, лицензии атрибутируются в паспорте
(перечень в отчёте компилятора). Стиль карточек: 2–4 факта, без оценочных
суждений; медицинские/правовые/финансовые факты в срез НЕ включать (RED).
[ОБЯЗ] «Не знаю»-честность: произвольный фактический вопрос вне карточек →
каркас UNKNOWN_HONEST + предложение занести в очередь дообучения (вопрос
оператора «дообучи» — тоже карта: снимок лемм сохраняется, ответ появится после
наполнения KB). Это лучше галлюцинации.

22. ОЧЕРЕДЬ ВОПРОСОВ Curiosity: 4 ИСТОЧНИКА, ПРИОРИТЕТЫ
--------------------------------------------------------------------------------
  1) Диагностические (высший): незакрытые гипотезы why-дерева, неразрешимые по
     логу. «Арматуру k136hl переключали вручную между сканами 30 и 40?» —

  2) Паспортные: пустые поля RunPassport (MainC, SkL, Scenario, KitVersion).
     Ответ записывается в паспорт только после подтверждения оператора.
  3) Знакомственные: пробелы профиля (имя, роль, ты/вы). Один раз, навсегда.
  4) Общеобразовательные: после GRAY-ответа — вопрос из поля curiosity карточки.
     Низший приоритет, жёсткий throttle.
[ОБЯЗ] Тормоза (иначе ассистент — дознаватель):
  maxConsecutiveQuestions = 2;  minMessagesBetween = 3;
  perTopicCooldown = 10;        sessionQuestionCap = 15;
  offSwitch = «не спрашивай» (настройка + команда в чате).
[ОБЯЗ] Выбор кандидата детерминированный: score = priority × freshness ×
(1 − askedRecently); seed от плана. Вопросительные каркасы (OPEN/CLOSED/CHOICE)
строятся тем же Realizer — «Сколько подсканов на тик в этом прогоне?»
синтезируется из лемм, не хранится строкой.
[ОБЯЗ] Пытливость работает на диагностику: главный выигрыш — вопросы,
которые сужают локализацию.

23. РЕГИСТРАЦИЯ И ПРИЁМ ОТВЕТОВ: AnswerIntake
--------------------------------------------------------------------------------
[ОБЯЗ] Каждый заданный вопрос регистрируется как PendingQuestion(Id, Target,
TargetId, Kind, ExpectedSlots, AskedAt, Retries). AnswerIntake перехватывает
следующую реплику ДО обычного NLU:
| Тип ответа     | Леммы-маркеры                     | Действие                     |
|----------------|-----------------------------------|------------------------------|
| Подтверждение  | да, ага, угу, верно, точно,       | целевое обновление (24)      |
|                | конечно, именно                   |                              |
| Отрицание      | нет, неа, неверно, ошибаешься     | инверсное обновление         |
| Факт-значение  | число/имя/дата/слово-числительное | нормализация → слот          |
| Незнание       | не знаю, затрудняюсь              | asked, unresolved; веса не   |
|                |                                   | трогаем                      |
| Отказ          | не хочу, пропусти, потом          | закрыть; cooldown ×2;        |
|                |                                   | blacklist темы               |
| Коррекция      | «нет, я имел в виду…»             | откат последнего обновления +
|                |                                   | переспрос (≤1)               |
| Встречный      | вопросительные леммы              | отложить pending (2 сообщения),
| вопрос         |                                   | ответить, вернуть нить       |
[ОБЯЗ] Если ответ не подходит под схему слотов — ОДИН вежливый переспрос,
затем сброс (не мучить).

24. ЦЕЛЕВЫЕ ОБНОВЛЕНИЯ (самое ценное)
--------------------------------------------------------------------------------
[ОБЯЗ] Гипотеза (байесовское, детерминированное): да → w×=1.6; нет → w×=0.4;
нормировка Σw=1; пересортировка → НОВАЯ локализация в следующем же ответе.
Пример: М12, «затирка счётчика» w=0.6; вопрос «Счётчик условий инкрементируется
после каждого FR_C?» — «нет» → w=0.86 → «Тогда область поиска сужается: блок
178xxx, процедура FR_C, строка инкремента. Показать?»
[ОБЯЗ] Паспорт: число → MainC/SkL; текст → Scenario; подтверждение «Понял:
{факт} записал в {цель}. Подтверждаете?» — только после «да» OperatorConfirmed.
[ОБЯЗ] Профиль: имя/роль/интересы → долговременная память (KtkData).
[ОБЯЗ] Общая беседа: факты о собеседнике («болею за Спартак») → interests,
используются в будущих мостах.
[ОБЯЗ] После обновления — синтезированное подтверждение K7 (отражение
факта, вариативное) + решение follow-up (K8).

25. ПРИМЕР ДИАЛОГА (требование к порождению; повтор прогона — идентичный текст)
--------------------------------------------------------------------------------
  Оператор: Привет, как тебя зовут?
  Владимир 26: Доброе утро, Владимир. Меня зовут Владимир 26 — цифровой
  рецензент, версия KB от 28.11.2026. Мы с вами тёзки. Как ваше настроение?
  Оператор: Нормально. Как дела у тебя?
  Владимир 26: Дела рабочие: журнал разобран, 483 узла, 12 находок, самотест
  зелёный. Тревожит М9 — затухание немонотонное. Кстати, для паспорта: что
  делали в этом прогоне?
  Оператор: Закрывали k136hl вручную, потом открыли.
  Владимир 26: Понял: сценарий «ручное переключение k136hl» записал в паспорт.
  Это важно для М12: переключение вручную было между сканами 30 и 40?
  Оператор: Да.
  Владимир 26: Тогда гипотеза «затирка счётчика» усиливается: вес 0.86. Область
  поиска — блок 178xxx, процедура FR_C, инкремент счётчика условий. Открыть

38. РИСКИ
--------------------------------------------------------------------------------
  - Русская морфология сложна (чередования, беглые, разносклоняемые): правила
    покрывают ~95%, остальное — исключения из дампа; неизвестная лемма не

  - Свобода small talk ограничена каркасами: GRAY-ответы композиционны, но
    «остроумия» не будет — осознанная цена аудируемости.
  - Пытливость может раздражать — тормоза, blacklist, выключатель ОБЯЗАТЕЛЬНЫ.
  - Классификация ответов — лемматические эвристики; сложный сарказм не
    распознаётся (и не надо).
  - Контент общего среза — курируемая работа (наполнение/выверка, лицензии),
    не кодовая; без него GRAY работает только на встроенных карточках.
