## 0. Контекст проекта (обязателен к прочтению целиком)

Проект Pinchess — WinForms-приложение (C#/.NET 8) для переборного синтеза переобвязки
теплообменной сети установки АТ-5 Ильского НПЗ. Цель поиска — максимум рекуперации Q (МВт)
при фиксации топливной экономии печей. Актуальная версия v25.

Рядом с этим файлом лежит ПОЛНЫЙ КОД (файл кода от ассистента-принимающего; структура):
- `src/Pinchess.Engine/` — ядро: Domain (ProjectSpec/FlowSpec/ApparatusSpec/State/AppInstance/SplitSpec),
  Sim (Simulator: волновой расчёт сети, coarse/fine), Search (SearchEngine: StrictBnB + BeamSearch,
  Moves/StateOps — генерация и применение ходов R1/R2/R4/R5/R1Shift/R2Shift/R3Split,
  UpperBound/PtaCascade — верхние грани, Canonizer — канонические ключи),
  Furnace (FurnaceModel: печь как терминирующий потребитель холодного потока),
  Grid (GridProjectMapper — отображение «сетчатой диаграммы» на схему),
  Validation, Io (ProjectJsonIO, Checkpoint), Economy (EconomyModel: NPV/IRR),
  Objective (IObjective: QMaxObjective, FurnaceFuelObjective);
- `src/Pinchess.App/` — WinForms UI: SchemeForm (канва сетчатой диаграммы: полоски-аппараты на
  температурной шкале, кружки-связки, анимация потока), SchemeGridForm/GridTableForm
  (сетчатая диаграмма как таблица T×аппарат), Theme (тёмная тема), PDF-отчёт (PdfSharp, MIT);
- `src/Pinchess.Cli/`, `runner/At5V3` — консольные прогоны (режимы configs/beam);
- `tests/Pinchess.Tests/` — xUnit, ~230 тестов; факт-сцена АТ-5 в At5FixturesV3 (метод FactSceneV3,
  эталонные цифры: К1 25,243 / К2 26,353 / К3 27,846 МВт; печи 2310/2161/1960 м³/ч).

Ключевые доменные факты (для шага A):
- Холодные потоки греются сетью от TStartC к TTargetC, горячие остывают; сеть обменивается теплотой
  между потоками через аппараты (Q_i, вход/выход температуры хранятся в AppCalc после симуляции);
- Пинч-анализ: ΔT_eff = TminC − max(SleepTolC, DtolOverlapC) − TauMarginC (в коде — UpperBound.UbGlobalMw
  → PtaCascade.QRecoverableMw). PtaCascade уже считает «problem table» (интервальный метод по всем
  концам потоков): Q_rec = ColdTotal − Q_H_min. Контрпример ревьюера: hot 100→50, cold 20→40, τ=10,
  мощности 1 МВт/К ⇒ ровно 20 МВт.
- В поиске: State = Committed (список AppInstance: аппарат+поток+сторона+позиция) + Splits (деления
  потока на ветви с долями); CanonicalKey — канонический ключ состояния; M1-лексикография: при равном Q
  меньше MountChanges, при равном M1 — меньший ключ по Ordinal.

Правила чужого кода: детерминизм (никакого неупорядоченного перечисления словарей; сортировки с
StringComparer.Ordinal), тест-стиль — xUnit [Fact], имя_теста_фиксирует_инвариант.

     (б) новые файлы кода — каждый в отдельном блоке с полным путём (например
         `src/Pinchess.Engine/Pinch/CompositeCurves.cs`) и заголовком-шапкой:
         первая и последняя строка файла — комментарий `//` (любого вида), внутри — код;
     (в) тесты — отдельным файлом в `tests/Pinchess.Tests/`;

1.3. Всё детерминировано: сортировки — с явным компаратором (Ordinal), Dictionary.Values только

1.5. Каждый шаг сдавай отдельно и жди вердикта принимающего: «принято» → следующий шаг;

1.6. Если считаешь шаг невыполнимым без изменения правил — остановись и запроси решение,

## 2. Шаг A. Композиционные кривые пинч-анализа (данные + рендер-контракт)

Цель: классический pinch-диаграммный вид на канве приложения — сдвинутые составные кривые
(hot/cold composite curves), пинч, Q_H_min/Q_C_min, зум/пан, hover-информация по сегментам.
Требуется КРАТНОЕ развитие визуала: новый экран (форма/панель) — не правка существующей канвы.

2.1. Новые файлы (твои):
- `src/Pinchess.Engine/Pinch/CompositeCurves.cs` — ЧИСТЫЙ расчёт, без WinForms:
  - вход: ProjectSpec (потоки+аппараты) ИЛИ альтернативный путь — построение по фактической
    симуляции состояния (State → Simulator coarse) — РЕШИ И ОБОСНУЙ, что берёшь за вход и почему
    (подсказка: у графика «факт» и «целевой» предел — два разных графика; оформи оба);
  - выход: `CompositeCurvesResult`: два полигона (hot/cold) как упорядоченные списки точек
    (T_сдвинутая_шкала, H_кумулятивная, [метка сегмента]), координата пинча (T*, H*), QHmin, QCmin,
    ΔT_eff; ИНВАРИАНТЫ, которые ты обязан явно проверить тестами:
    (i) в точке пинча зазор между кривыми = 0 (±eps);
    (ii) слева от пинча вертикальный зазор равен QHmin, справа — QCmin;
    (iii) кривые непрерывны по H (монотонно неубывающие по Q);
    (iv) ΔT_eff применяется РОВНО как в PtaCascade (сдвиг горячих на −ΔT_eff/2, холодных на +ΔT_eff/2 —
      сверяй со сдвигом, реализованным в UpperBound/PtaCascade, и ПРОКОММЕНТИРУЙ сверку);
  - детерминизм: точки одной кривой сортированы стабильно; повторный вызов — байт-в-бит тот же список.
- `tests/Pinchess.Tests/CompositeCurvesTests.cs` — минимум 6 тестов: контрпример ревьюера (должен
  дать ровно 20 МВт и совпасть с PtaCascade), монотонность, зазор в пинче=0, повторяемость,
  факт-сцена (QHmin+QCmin сходится с QRec PtaCascade на той же ΔT_eff — проверь тождество и
  напиши его формулой), тест «курв's ноль аппаратов» не крашится (пустые кривые).

2.2. Формулировка рендер-контракта (скелет, БЕЗ привязки к конкретной форме):
- интерфейс `IPinchView` (данные → геометрия): функции T→X, H→Y, обратные X→T, Y→H,
  зум/пан (центр-масштаб, wheel+drag), маски клипа; РЕАЛИЗОВАННЫЙ — только на данных-координатах,
  без Graphics (WinForms — следующий шаг, не твой);
- декларация expected-файла следующего шага: что принимать в рендер (какие поля результата).

2.3. Запрещено: менять PtaCascade/UpperBound; тянуть WinForms в Engine; выводить в UI.

## 3. Шаг B. Дифф «было/стало» с анимацией перемещений (визуальный протокол)

Цель: на канве факт-схемы показать ПЕРЕХОД от состояния fact (К1) к найденному оптимуму (К3)
как анимированные перемещения аппаратов между позициями цепочек + новые сопряжения + байпасы.

3.1. Новые файлы:
- `src/Pinchess.Engine/Diff/SceneDiff.cs` — чистый расчёт:
  - вход: два State (before/after) одного ProjectSpec;
  - выход: `SceneDiffResult { List<DiffOp> }`, где DiffOp — одна из операций с ЕДИНСТВЕННЫМ
    полем-тегом вида: AppMoved(AppId, HotFrom→HotTo, ColdFrom→ColdTo), AppNew(AppId, hot, cold),
    AppRemoved(AppId), BypassToggled(AppId, before, after), SplitChanged(FlowId, before, after),
    PositionShift(AppId, FlowId, Side, oldPos→newPos) — ВЫБЕРИ И ОБОСНУЙ финальный набор операций
    (требование: операции непересекающиеся, дифф уникален, сумма операций обратима — «after → diff⁻¹ → before»);
  - алгоритм сопоставления: только по ApparatusId (имена стабильны), затем по (FlowId, Side);
    сплиты — по FlowId; порядок операций — детерминированный (Ordinal);
  - инвариант-тесты: симметричность (diff(before,after) уникально сводит after к before),
    самодифф пуст, факт-сцена vs BeamBestState (в руннере есть эталонное состояние — попроси
    у принимающего код, если рядом нет: метод BeamBestState файла runner/Program.cs) даёт
    набор из 15 аппаратов без операций AppRemoved (все аппараты сохраняются в оптимуме).
- `src/Pinchess.App/Diff/DiffTimeline.cs` — СКЕЛЕТ анимации (можно с Graphics-заглушками,
  помеченными `// TODO(render)`): таймлайн операций (порядок, длительности, easing), модель
  промежуточных позиций t∈[0;1] (аппарат движется по полилинии маршрута — маршруты не рисуй,
  только координаты); правила: не блокировать UI-поток (таймер WinForms), отмена (CancelationToken),
  повторяемость: одинаковые before/after → одинаковый таймлайн.

3.2. Интеграционная точка (единственная): SchemeForm — маркер, куда должен втыкаться
     DiffTimeline (найди место отрисовки аппаратов; якорь приведите с контекстом ±3 строк).
