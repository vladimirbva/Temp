гидравлика+тепло+составы, решатель по тикам, сцены в JSON. Полный код r42 известен как
«код 42» (3 217 686 Б) — файл «код 42 - не трогать.txt» лежит в этой же папке ГВР (BUDcad/),

панели BuildStreamsTab/BuildNetTab/BuildTargetTab/top-панель PinchGridWindow; Size 1180×720,
MinimumSize 900×600; поля _chkAxes/_axesShifted; режим «Фактические оси» в PlotPaint с
подписью-пояснением). Зоны дампа сместились — работай по якорным строкам (раздел 2).

Принятые решения владельца (PSR BUDcad):
• Р-16 — КУРАТОРСКИЙ импорт пинч-потоков как проектных целей (вместо текущего ImportFromScene,
  тянущего каждую трубу |ΔT|≥2 °C как пинч-поток: шум, смешение фактических T с целевыми —
  главный источник «непонятности»);
• Р-17 — сетчатая диаграмма: классическая сетка Линнхоффа, ось X = накопленная тепловая нагрузка
  (реализуется в Сп1: единый HenLayout-движок, эскиз принят, код — параллельная задача TASK_6);
• Р-18 — документ-вкладки Схема|Пинч|Отчёт|Журнал + докируемый пинч; PinchGridWindow сохраняется;
• порядок спринтов: Сп0 (r43: pinpoint-правки панелей) → Сп1 (TASK_6, в работе) → Сп2 (этот) →
  Сп3 (вкладки) → Сп4 (DPI/отчёт).
Диагноз из TASK_2 (принят): ImportFromScene тянет каждую трубу |ΔT|≥2 как поток; светлое меню
MainForm при тёмной теме (резерв Сп0/Сп4 — в Сп2 не смешивать, но отдельным пунктом предложить
можно); рекомендации Б1–Б5.
Димино замечание 2 (26.11): при ΔTmin=10/20/100 композитные кривые «лежат на линии» — НЕ дефект
расчёта: кривые строятся в сдвинутых осях (горячая T−ΔTmin/2, холодная T+ΔTmin/2), зазор в пинче
= 0 (касание — норма), у верха QHmin, у низа QCmin. Дефект — отсутствие объяснения в UI. В r43
уже добавлены подпись-пояснение и переключатель «Фактические оси» (по умолчанию — сдвинутые).

3. ЗАДАЧА (этап 1: эскиз UX, БЕЗ кода)
========================================================================
Спроектируй Сп2 — UX пинч-анализа. Три узла:
1. Кураторский импорт (Р-16). Экран/мастер импорта пинч-потоков из сцены: кандидаты (трубы
   с теплоносителем, аппараты с тепловыми потоками), дефолтные предложения (сортировка по |Q|,
   группировка), пользователь выбирает подмножество и назначает тип (горячий/холодный/утилита);
   T-цели задаёт пользователь (по умолчанию — фактические крайние температуры объекта); маппинг
   поток↔объект (обратная связь: изменение сцены → ревалидация потока; поведение при исчезновении
   объекта); редактирование до расчёта; совместимость с существующими «кейс»-файлами XLSX
   SpreadsheetML (чтение сохранённых наборов).
2. Карточка целей. Ввод/отображение проектных целей: целевые T входов/выходов, требуемые
   нагрузки; соответствие «цель ↔ фактическое» (цветовая индикация); связка с таргетингом
   (ΔTmin, QHmin/QCmin/Rec); как цель влияет на синтез (область превышения ΔTmin, предупреждения
   о недостижимости).
3. Plain-language предупреждения. Словарь предупреждений PinchDesign.Warnings → человекочитаемые
   формулировки (причина + что делать + куда смотреть); классификация: информационное /
   предупреждение / блокирующее; где отображаются (вкладка Пинч, журнал, тултипы на диаграмме);
   порог warning при визуальном пересечении композитных кривых в фактических осях — ОПРЕДЕЛИТЬ
   ЗДЕСЬ (информационный/блокирующий — открытый вопрос из TASK_5, перенесён в Сп2).
Также дай рамки навигации вкладок Схема|Пинч|Отчёт|Журнал (Р-18) — только концепция (территория
Сп3), чтобы Сп2 не блокировался.

Формат ответа:
1) эскизы экранов (текстовые/ASCII-схемы): элементы, состояния, поток данных;
2) поток данных: откуда кандидаты импорта, где хранится набор потоков, как связан с PinchDesign;
3) перечень зон кода, которые затронет этап 2 (якоря дампа r42/r43) + план Сп2 по этапам;
4) риски и вопросы владельцу стандартной формулировкой.
Код-диф в ЭТОМ ходе не нужен — приёмка эскиза ассистентом (КП4.1г: этап 2 после приёмки).
Сборку r44 и Сп1 выполняет ассистент-сборщик по TASK_6 (другой исполнитель) — твой эскиз
не должен ломать его зоны: избегай правок в PinchGridWindow.cs и HenLayout-областях.
