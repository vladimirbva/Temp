0. О ПРОЕКТЕ (что такое BUDcad сегодня)
================================================================================================
BUDcad 2.3 (в приёмке «2.2») — Windows-приложение C#/.NET 8 (WinForms), 2D-симулятор
технологических схем: гидравлика + тепло + составы (молярные, фазовые состояния), решатель по тикам
(dt = 1 с, таймер UI), сцены в JSON. Ядро — собственный численный движок, БЕЗ внешних
библиотек-зависимостей (осознанное решение владельца: замкнутый код, без NuGet-новинок).
Основные подсистемы:
- Схема: сцена из объектов (ёмкости/сепараторы/реакторы/колонны/баки/насосы/трубопроводы),
  штюцеры, ветви; рендер GDI (+Skia-ветка), панель свойств, узлы/рёбра, Undo, сохранение в JSON.
- Решатель: GgaSolver.cs (маркер дампа r49 ~26021) — сеть собирается в BuildNetwork
  (HE, HighEfficiencyEngine.cs ~4495), Ньютон-подобный метод с аналитическим якобианом
  (ReffFull R37; EdgeEval — единая оценка звена q/g/dQdPin), плавные танх-клампы, qMin,
  гейты; в динамике (SimMode) узлы ёмкости несут податливость C_i (CapacityCells:
  cap = vGas/max(0.05, GasPressure) + vLiq·5e-5, C_i = cap/max(1, Nozzles.Count);
  capP0 = HydrostaticP(obj, z_nz) — столб той же функцией; решение Р-9: P_node — неизвестная
  Ньютона, перезапись P после Solve снята). Ребро несёт геометрический столб head = ρg(Zb−Za).
  Водослив (R38): WeirQPot/WeirSign, закон 0.62·(2/3)·√(2g)·π·D·s(h/δ)·h^1.5, δ=0.01 м,
  гейт приёмника — танх на dpNet; WeirSign ставится ТОЛЬКО от книги ПРОШЛОГО тика (бутстрап).
  После Solve — вбросы в ячейки «после» решателя (перелив, компрессия). SolveMs — замер на тик.
- Пинч-модуль (Сп0–Сп2, r45–r49, свежее): PinchEngine (композиты, пинч, цели Target→Design),
  HenLayout.cs (Сп1: единый layout-движок сетчатой диаграммы — ось X = накопленная тепловая
  нагрузка Р-17, рендер VectorScene → GDI/Skia, пиксельные golden-эталоны, контракт «не
  сортировать Exchangers»), кураторский импорт (PinchImportModel.cs — извлечение потоков из
  расчёта гидравлики, PinchImportWizard.cs — трёхшаговый мастер, шкала отклонений 5/10%),
  кейс-файлы Kliche (XLSX-«клешё»: таблица потоков + утилиты, ЭСП-экономика; сейчас — параллельная
  задача TASK_11: лист «Маппинг» в кейсе).
- Диагностика: DiagEvent, ANOM (анализ несходимости), SolveMs, статус-сегменты (r47), FPS.
- Приёмка: 450+ Э-эталонов (регресс ×2), InvariantCulture, детерминизм байт-в-байт, xUnit.
Правила проекта: только собственные численные методы; правки ядра — через отдельные TASK;
сборки rN по журналам R-fixed в шапке дампа.

2. ГЛОБАЛЬНЫЙ ВОПРОС (широкая постановка)
================================================================================================
«Переосмысли BUDCAD новыми глазами». Дать широкий концептуальный разбор ТРЁХ направлений
и свести их в единую архитектурную перспективу. Владелец оценил объём как «эквивалент 3–4
мощных спринтов» — отвечает на это не объёмом текста, а ГЛУБИНОЙ и КОНКРЕТНОСТЬю.

Направление А. РЕШАТЕЛЬ 2.0 — событийная гибридная динамика.
Замена «решателя по тикам с клампами» на честный гибридный DAE-подход:
а) семантика тика (UI-синхронизация, dt=1с, SolveMs) сохраняется КАК ОДИН ИЗ РЕЖИМОВ;
б) закрываются дефекты 1.3–1.6 на уровне АРХИТЕКТУРЫ (не клампами);
в) фазово-высотный отбор по штуцерам: режим штуцера («только газ» / «газ+жидкость» /
   «только жидкость») определяется уровнем ёмкости относительно ОТМЕТКИ штуцера; пересечение
   уровня со штуцером = СОБЫТИЕ с хендлером. Спрос владельца: «получаем ли мы и динамику,
   и высоты, и разнофазные выходы?» — ответ обязан явно покрыть все три.
Аспекты (развёрнуто, каждый — разделом):
- Выбор интегратора: неявный BDF / Radau / DIRK — что и почему для этой сети (жёсткость,
  тысячи узлов, UI-ритм, детерминизм, воспроизводимость байт-в-байт). Сравнить с текущей
  «квазистатикой + податливостью C_i» — где нужна честная динамика, где хватает квазистатики.
- Событийная механика: корневые функции g(event)=0; детектор (уровень↔штуцер; P<Psat в верхней
  точке сифона; открытие/закрытие гейта; уровень=полнота); хендлеры (restart, проектор,
  сохранение шага); консервативность массы/энергии через событие (ΔM=0 в разрыве) —
  обязательное требование (дефект 1.5).
- Фазово-высотный отбор: модель расслоения (LiquidLevel уже есть), правило отбора по отметкам
  Z, гибридное состояние, НЕПРЕРЫВНЫЙ переход при переключении (согласование потоков, сохранение
  состава); частичное погружение (захват газа/эмульсия) — минимальная честная модель, не CFD.
- Разреженный якобиан: разделённые подсети, блок-треугольный порядок, переиспользование
  факторизации; аналитические производные EdgeEval уже есть → sparse-LU (CSC/CSR); порог
  перехода от полных матриц.
- Миграция 450+ зелёных Э-эталонов без «одного bang»: фазы 3–4 спринта, критерии приёмки,
  обратная совместимость JSON-сцен (новые поля — без поломки старых).

Направление Б. ПИНЧ-ПРОЕКТИРОВЩИК — из анализа в СИНТЕЗ сети теплообмена.
Сегодня: программа говорит «вот цели/минимум утилит», сеть HEN рисует человек. Предложить
концепцию автоматического СИНТЕЗА сети теплообменников и ретрофита:
- Постановка: pinch decomposition (над/под пинчем — уже есть в PinchEngine), MER-сеть
  (правила Linnhoff: сортировка по ΔT, CP-матрица, метод Composite Problem (CPM); LONR/CPI;
  эволюционные модификации: разрыв контуров малой нагрузки, идентификация константных петель),
  суперструктура + MILP (если MILP — как решать без внешних солверов? может, LP-структурная
  формулировка/эвристика), либо эволюционный алгоритм (GA/имитация отжига) поверх эвристики;
  выбор подхода — обосновать.
- Вход: потоки из кураторского импорта (r48) и кейса; ΔTmin; утилиты (цены, факт).
- Выход: сеть теплообменников (сопоставление потоков, нагрузки, зоны) → РЕНДЕР через готовый
  HenLayout (сетчатая диаграмма) + отчёт: рекуперация, утилиты, число аппаратов, области
  ретрофита (какие ручные связи оставить/добавить).
- Ретрофит: работа с СУЩЕСТВУЮЩЕЙ сетью (сохранённой в сцене) — минимальные изменения,
  Network Economy/NELT-подходы; где выигрываем больше всего на практике.
- Критерии приёмки: достигнутые цели против PinchEngine (не хуже ε), детерминизм, время
  синтеза (бюджет), читаемость результата пользователем.
- Границы: НЕ трогать PinchEngine/HenLayout API; синтез — новый модуль поверх.

Направление В. ЛИНТЕР СХЕМ / АВТОЭКСПЕРТ.
Систематический слой правил проверки сцены (не только DiagEvent на прогонах):
- Каталог правил (нужны КОНКРЕТНЫЕ категории и примеры, 30–100 правил):
  физика (кавитация на всасе, обратный поток, вакуумные карманы, потеря NPSH, дегазация,
  сифонные ловушки, двусмысленные переливы), инженерная практика (dead-legs, наклон конденсатных
  линий, размеры дренажей, анти-сиропон, свободные концы, изоляция фаз), топология (петли без
  сопротивления, параллельные ветви без согласования, избыточные клампы), эффективность
  (рекуперация ниже цели, утилиты выше факта, ЭСП-максимизация).
- Классификация: Ошибка (блокирует расчёт) / Предупреждение (видно, не блокирует) /
  Совет (оптимизация); plain-language объяснения (У3) с ПОДСКАЗКОЙ ГДЕ СМОТРЕТЬ (узел/ребро) и
  АВТО-ПРЕДЛОЖЕНИЕМ правки (кнопка «исправить» — с подтверждением пользователя).
- Инфраструктура: правило = функция над снимком сцены (без правки ядра), приоритезация по
  влиянию, дедупликация, подавление («не показывать снова»), связь с уже существующими
  DiagEvent/ANOM (не дублировать).
- Критерии: ложных срабатываний < X% на эталонных сценах; каждая рекомендация — объяснима;
  правила НЕ ломают решатель (read-only анализ).
- Аудит-канал: как связать с существующим Э-приёмкой (новые правила — новые Э-эталоны).
