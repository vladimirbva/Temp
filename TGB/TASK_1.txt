1. КОНТЕКСТ ПРОЕКТА С НАЧАЛА (ты в новом окне — всё ниже самодостаточно)
========================================================================
BUDcad — Windows-приложение (C#, .NET 8, WinForms) — 2D-симулятор технологических
схем: гидравлика+тепло+составы. Сетка узлов, решатель гидросети, сцены (JSON-проект).
Полный код BUDcad (r40, 179 файлов) у тебя В КОНТЕКСТЕ текущего чата (файл
«код 40 - не трогать.txt»). Актуальная база сейчас r42 (терминальный контракт не
менялся с v62), но для этого вопроса r40 достаточно.

ТЕРМИНАЛ (объект BUDcad) — «микропроцессор»: подгружает МЕТОД (.bmethod — JSON-
манифест, до 100 уравнений-строк). Порты метода синхронизируются со штюцерами
(соединениями схемы). После решения гидросети TerminalEngine исполняет уравнения
по тикам и выдаёт P_/T_/Q_ и составы Y1..Y40. Контракт уже исполнен в BUDcad
(v59–v63): подгрузка/штюцеры/реверс-тревога/Q-регулятор (секанта dP=(P−P_prev)·
err/(Q−Q_prev), кламп ±0.3 бар/тик, приоритет Q>P_)/параметры экземпляра/история.
Состав: X1..X40 — read-only вход, Y1..Y40 — выход (дефолт Yi=Xi, нормировка,
один состав на ВСЕ out-порты).

TGB (Terminal-Generator BUDcad) — ОСОБАЯ утилита: редактор/валидатор/версионер
методов ВНЕ BUDcad. Реализация НЕ начата. Заморожена, старт уже согласован.

КАНОН ВЕЛИЧИН (строго, менять нельзя): BuildVariables(m) = параметры манифеста →
на каждый порт 4 слота: <имя> (алиас расхода), Q_<имя> (м³/ч, со знаком:
входной порт + = «в терминал», выходной + = «из терминала»), P_<имя> (бар),
T_<имя> (°C) → промежуточные Outputs по порядку. Только чтение: параметры и
величины входных портов. Назначаемые: величины выходных портов и новые имена.
P_/T_ выхода применяются к границе out-порта в следующем тике; Q_<выход>
вписывается в сеть регулятором (v62); X→Y на все out-порты.

АРХИТЕКТУРА, УЖЕ ПРИНЯТАЯ РЕВЬЮ (пересматривать не нужно, учитывать):
- Core-библиотека BUDcad.Methods.Core (net8.0, без Windows-зависимости): модель
  BMethodModel.cs + валидатор BMethodLoader + компилятор BMethodExprCompiler +
  сериализатор + golden-fixtures. TGB и BUDcad ссылаются на ОДИН проект.
- Детерминированный writer: Save(Load(x)) == x байт-в-байт; hash меняется только
  с содержимым (SHA256 от текста файла; BUDcad сверяет при подгрузке).
- Правило «одного валидатора»: TGB вызывает только BMethodLoader.Parse/Validate/
  CompileAll/BuildVariables/InputVariableNames/HashOf; свои сообщения запрещены —
  расхождение = дефект. TGB — «тонкий» UI над Core.
- Правило сопряжения: TGB ничего не требует от BUDcad сверх уже исполняемого;
  новая возможность BUDcad → сначала расширение BUDcad (КП1.4), потом в рамку TGB.
- Ревью приняло: песочница-прогон вместо «Диагностики»; лимиты парсера+fuzz;
  undo/redo и autosave в %AppData%\TGB; честная тёмная тема + PerMonitorV2 DPI +
  golden-image предпросмотр; diff-баннер при переименовании портов + авто-версия +
  history[] в манифесте; мини-IDE в «Математике»; first-run полировка (resx,
  crash-лог). 15 точек сопряжения ТЗ §12 (общая модель; валидатор только
  BMethodLoader; компилятор только BMethodExprCompiler; hash; подгрузка только
  TerminalApply.PickAndLoad/ApplyTo; штюцеры = имена портов; каталог BUDcad_Methods;
  format=1 фиксирован; сообщения валидации = сообщения BUDcad; сериализация в
  проекте BUDcad; параметры экземпляра v62 R3).

ТЕХНОЛОГИЧЕСКИЙ СТЕК BUDcad (текущий): WinForms на .NET 8; собственная отрисовка
сцен (GDI+); многовкладочный UI; локализация минимальная; сборка через csc-конвейер
владельца (не MSBuild, конвейер: selfcheck --deep, etalon_sync, xUnit -parallel none,
pack + контрольная сборка из распакованного пакета).

ОТКРЫТЫЕ РЕШЕНИЯ, КОТОРЫЕ ПРИДЕТСЯ ПРИНЯТЬ ПЕРЕД Ф1 (на них и опираются вопросы):
1) Демо-прогон NaN: сейчас блокирующая ошибка (правило №14). Кандидат —
   декларируемые демо-значения входов в манифесте; перевод в предупреждение
   обязан пройти паритет в ОБОИХ потребителях.
2) kind порта (Q/T/P): декларативная подсказка + единицы в UI.
3) X1..X40 при НЕСКОЛЬКИХ входных портах: семантика не определена (сейчас
   BUDcad берёт состав из первого штюцера со значимым составом; эталона нет).
4) Коллизии имён (параметр Q_in, порт Y1, Output как алиас) — валидатор
   фикстурами.
5) Один Y-состав на все выходы — крупное предупреждение в UI.
6) Authenticode: отложить или самоподписанный.

ИСХОДНИКИ ДЛЯ СВЕРКИ (твой контекст): ТерминалEngine.cs (исполнение тиков,
порядок выражений), BMethodLoader.cs / BMethodModel.cs / BMethodExprCompiler
(парсер/валидатор/компилятор, VarNames), TerminalApply (подгрузка/применение),
формы терминалов (настройка экземпляра), PinchStudio (пример «сложного» UI в
BUDcad — на что уже способен WinForms-код проекта), SessionLog/журнал ошибок.
Если для ответа нужен ДОСЛОВНЫЙ текст ТЗ TGB v1.1 (22 КБ) — заявить в конце
ответа в вопросах к владельцу; выжимка выше — достаточна для рекомендаций.

2. ГЛОБАЛЬНЫЙ ВОПРОС
========================================================================
TGB — фактически мини-IDE поверх чужого компилятора, в стеке WinForms, для
пользователя-инженера (не программиста). До старта Ф1 нужен твой свод
рекомендаций по архитектуре/дизайну/вводу, чтобы зафиксировать ТЗ v1.2 и не
перепахивать UI после Ф3. Ответ дай по АСПЕКТАМ ниже: по каждому —
рекомендация, обоснование, критерии выбора, риски, ограничения. Код — только
иллюстрация.

А1. КАРКАС И СТЕК. WinForms (как BUDcad, переиспользование стиля и наработок)
    vs WPF vs Avalonia vs гибрид (WinForms-оболочка + специализированные
    контролы). Критерии: качество редактора кода (подсветка, автодополнение,
    свёртка), DPI-масштабирование, трудоёмкость, риск отступать от стека
    BUDcad, поддержка конвейера сборки владельца (csc-конвейер!).
А2. МЕТОД ВВОДА УРАВНЕНИЙ (главный вопрос). Метод — список уравнений-строк
    (имя ← выражение) с каноническими величинами. Как делать ввод интуитивным
    для инженера: (а) текстовый редактор с грамматикой BMethodExprCompiler
    (подсветка/автодополнение канонических имён, inline-ошибки от валидатора);
    (б) структурированная таблица «имя ← выражение» с отдельными ячейками;
    (в) гибрид (таблица строк + расширенная ячейка-редактор с подсказками);
    (г) что-то ещё (диаграмма потоков величин?). Учесть: порядка ≤100 строк;
    read-only величины нельзя назначать (валидатор это ловит — UX должен
    предупреждать ДО валидации?); подсказки по единицам (Q м³/ч, P бар, T °C);
    порядок строк значим (поздние ссылки на ранние Outputs).
А3. РАБОЧИЙ ПОТОК. Создание метода с нуля: порты → параметры → уравнения →
    проверка → сохранение → подгрузка в BUDcad. Как организовать вкладки/
    визард/одиночный экран, чтобы новичок не заблудился, а опытный не страдал;
    предпросмотр (golden-image), вкладка «Проверка» (сообщения валидатора),
    песочница (прогон на демо-входах) — где их место в потоке.
А4. РЕДАКТОР ПОРТОВ/ПАРАМЕТРОВ. Таблицы портов (имя, направление in/out,
    kind Q/T/P — подсказка+единицы), параметров (имя, тип, дефолт, диапазон?).
    Как предупреждать о коллизиях имён и ревизиях (diff-баннер уже принят).
А5. ОТКРЫТЫЕ ВОПРОСЫ §17 ТЗ: имя приложения; TGB в solution BUDcad_2.1.sln
    или отдельное решение (учитывать Include BMethodModel.cs, а не ссылку);
    лимит 100 выражений — жёстко/предупреждение; нужна ли вкладка
    «Диагностика» с TerminalPortValue (read-only) в Ф1.
А6. ОТКРЫТЫЕ РЕШЕНИЯ при возобновлении (см. список выше): какие демо-значения
    входов целесообразно декларировать в манифесте (структура поля, дефолты,
    как мешают NaN); семантика X1..X40 при нескольких входах — рекомендация
    (сумма? приоритет первого? запрет более одного входного порта со
    составом?); как UI подсказывает «один Y-состав на все выходы».
А7. РИСКИ И ЛОВУШКИ, которые должен снять дизайн: локаль (запятая в JSON —
    только InvariantCulture при записи); hash меняется при любой правке —
    предупреждать о повторной подгрузке; правило сопряжения (не требовать от
    BUDcad нового); расширения синтаксиса запрещены в Ф1 — как UX живёт с
    этим ограничением.

Формат ответа: содержательные рекомендации по А1–А7 с обоснованиями и
критериями; сводка «решений владельца, которые ты считаешь правильными
принять в v1.2»; риски внедрения. Смоуки/прогоны не запрашиваются.
