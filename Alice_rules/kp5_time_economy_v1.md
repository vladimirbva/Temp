# КП5 — ЭКОНОМИЯ ВРЕМЕНИ И РЕСУРСОВ (политика v1.0)

**Версия:** 1.0 от 24.11.2026, по указанию владельца.
**Статус:** ГЛАВНОЕ правило экономии. Действует на ВСЕ проекты и ВСЕ операции,
в том числе внутри других КП. Не требует вызова — постоянно.
**Приоритет:** ниже только явных команд владельца; выше остальных проектных правил.

---

## 5.1. Окружение песочницы (SDK, зависимости, окружение)

- SDK/окружение/зависимости для проекта устанавливается ОДИН РАЗ в постоянное хранилище.
- Повторные запуски НЕ переустанавливают окружение: восстановление — КОПИРОВАНИЕМ из
  хранилища (сохранённые пакеты/кэш), а не повторной установкой из сети.
- Вести скрипт-восстановитель окружения (один файл на проект): что нужно, откуда берётся,
  как проверяется работоспособность после восстановления.
- Если окружение сломалось: сначала попытка восстановления из хранилища, переустановка —
  только если восстановление невозможно.
- Не создавать «параллельных» окружений без необходимости; одно окружение на проект.

## 5.2. Тесты (объём тестирования по этапу)

- Промежуточные проверки «на ходу» — МАЛЫЙ пакет: 10–40% целевого объёма тестов
  (ключевые инварианты + смок-тесты изменённого). Полный пакет — НЕ на каждом ходу.
- ПОЛНЫЙ пакет тестов (КП1.2) — только: финал проекта, приёмка владельца, КП1.1 (полная
  сборка), явная команда владельца.
- Тесты НЕ дублируют друг друга: повторный тест того же — не добавлять, если ничего не менялось.
- При изменении кода прогонять в первую очередь тесты, покрывающие изменённое; остальное —
  только при сомнениях.

## 5.3. Отладка (порядок и инструменты)

- Мини-сцена ПЕРВОЙ: воспроизводить баг на минимальной сцене/примере, не на всей сборке.
- Зонная трассировка: локализовать проблему зонами (модуль/функция), не трассировать всё подряд.
- Инвариант-чекеры: писать проверщики устойчивых свойств и запускать их — они ловят большинство
  ошибок быстрее отладки по шагам.
- Снапшоты состояния: фиксировать состояние до/после подозрительных операций, чтобы не
  проигрывать долгие сценарии повторно.
- Headless ПЕРЕД UI: логика отлаживается без интерфейса; интерфейс подключается после того,
  как логика стабильна.
- Не копать «наугад»: сначала локализация, потом правка, потом повторная проверка.

## 5.4. Файлы (чтение, правки, выдачи)

- Якорное чтение: НЕ переписывать большие файлы ради мелких правок — читать и менять только
  нужные фрагменты (по якорям/строкам).
- Предфлайт-якоря: перед масштабными правками — зафиксировать «якоря» (контрольные точки:
  строки/заголовки/хэши), чтобы проверить, что правка попала туда, куда надо.
- Патчи более 3–5 мест — только с предварительным dry-run (сначала пример применения,
  потом массовое применение).
- Манифест выдач: вести ОДИН сводный манифест выданного (куда, что, размер, контрольная сумма,
  дата) — чтобы не «дёргать» владельца повторными выдачами и не терять выдачи.
- Ротация хранилища: старые/неактуальные версии — по согласованию, не накапливать мусор.
- Выдача сжато: не выдавать полными файлами то, что можно выдать дельтой/выпиской.

## 5.5. Планирование ходов (как работать за сессию)

- Разведка батчами: собирать нужную информацию пакетами вызовов, а не по одному,
  избыточные вызовы не делать.
- Инкрементальные сборки: строить сборку по частям с проверками, а не «одним махом»
  с полным прогоном после каждой мелкой правки.
- Тяжёлые сборки/прогоны — ПОСЛЕ карточек выдачи владельцу (не держать владельца в ожидании).
- Точка входа «start_here»: на каждый проект — файл-указатель (где что лежит, что актуально,
  с чего продолжить), чтобы не «восстанавливать память» по старым чатам.
- Один срез истины: НЕ хранить несколько версий «правильного» состояния проекта одновременно.

## 5.6. Приоритет правил

- При противоречии правил: явная команда владельца — выше всего; далее — данный документ (КП5);
  далее — правила проектов; далее — общий регламент.
- КП5 НЕ отменяет качество: экономия времени — не за счёт проверки результата.
