# КП5 — ПОЛИТИКА ЭКОНОМИИ ВРЕМЕНИ

**Версия:** 1.0 (21:0x 24.11.2026, по указанию владельца).
**Назначение:** универсальные правила экономии времени — применимы ко ВСЕМ проектам,
ходам и типам работ, без привязки к конкретным проектам. Не отменяет КП1–КП4:
при конфликте действует правило «минимальный объём, достаточный для надёжного
результата»; полный пакет — только на контрольных точках (см. 5.6).

---

## 5.1. Окружение песочницы: устанавливать РАЗ и хранить

1.1. Все SDK, runtime-среды и пакетные кэши (NuGet, npm/pnpm, компиляторы и т.п.),
которые нужны для ведения и отладки проектов и переустанавливаются после каждой
очистки песочницы, ОБЯЗАТЕЛЬНО размещать в постоянном хранилище.
1.2. Установка «с нуля» — только один раз. Все повторные чистки — восстановление
копированием из хранилища, не повторной установкой.
1.3. Восстановительные инструкции (как развернуть сохранённое) держать рядом
с пакетами; при чистках хранилища сохранённые окружения НЕ удалять — помечать
как постоянные.
1.4. Если крупный пакет не сохраняется целиком — сохранять кусками или держать
минимально достаточный набор для сборки и тестов проекта.
1.5. Профилировать окружение по стекам (отдельные каталоги на каждый стек):
восстановление после чистки — только нужный стек, а не всё подряд.
1.6. Рядом с пакетами держать скрипт-восстановитель (один запуск разворачивает
весь стек: SDK + кэши + компиляторы). Сборка скрипта — при первом же рабочем
ходе каждого нового стека.

## 5.2. Тесты: только целевые на промежуточных ходах

2.1. До финализации спринта прогонять ТОЛЬКО целевые тесты: от 10 до 40 %
от общего числа. Выбор — интеллектуальный, по типу изменений:
- аналитические гейты текущего этапа (новые эталоны спринта);
- тесты затронутых модулей/классов (по diff);
- направленные сцены по симптомам, которые чиним.
2.2. Правки без кода (CSS/JS-стили и т.п. при раздельном стеке) — сборка
основного кода не нужна вовсе, только смоук затронутой части.
2.3. ПОЛНЫЙ пакет тестов — только: финал спринта / выдача по КП1.2 /
приёмка владельца / релизная точка.
2.4. Контрольная точка после патча — точечный прогон по затронутым классам;
полный пакет добавляется только при подготовке выдачи.
2.5. Тестовый фильтр — по именам классов (групповой выбор), не по позиционным
именам тестов.

## 5.3. Отладка больших приложений

3.1. МИНИ-СЦЕНА ПЕРВАЯ. Любой новый баг по возможности сначала воспроизводится
минимальной сценой/конфигом, а не полным прогоном. Бонус: успешная мини-сцена
становится готовым эталон-тестом.
3.2. ЗОННАЯ ТРАССИРОВКА. Диагностический вывод включается не глобально, а по
зонам/классам; только вокруг подозрительного узла. После снятия симптома —
снос диагностических вставок. Глобальные логи — только на приёмке.
3.3. ИНВАРИАНТ-ЧЕКЕРЫ. Критичные узлы защищаются автоматическими проверками
инвариантов после каждого шага/тика; нарушение сразу указывает узел, а не
собирается ручным просмотром логов.
3.4. СНАПШОТЫ МЕЖДУ ЭТАПАМИ. Длинные конвейеры (многошаговые сборки,
конвертации, покадровые симуляции) сохраняют контрольные точки состояния:
откат к ближайшей точке вместо повтора всего прогона с нуля.
3.5. HEADLESS ПЕРЕД UI. Отладка логики — без интерфейса, через консольные
эталоны с фиксированным ожиданием; владельцу показывается финальный
проверенный результат, а не промежуточные экраны.
3.6. ОДНОПоточность ассертится, если движок однопоточный — расхождение в
модельном потоке считается дефектом сразу, а не «иногда падает».

## 5.4. Файлы, чтение и выдача

4.1. ЯКОРНОЕ ЧТЕНИЕ. Большие кодовые файлы читаются по якорям (имена процедур,
заголовки, дословные фрагменты) и их окрестностям, не целиком. Полное чтение —
только когда это действительно нужно (финальная сверка, выдача).
4.2. ПРЕФЛАЙТ-ЯКОРЯ. Перед точечными правками проверяются точные подстроки
(якоря), чтобы правки не падали и не портили файл.
4.3. ПАТЧИ ВМЕСТО РУЧНЫХ ПРАВОК. Правки больше 3–5 мест вносятся
воспроизводимым патч-скриптом с прогоном на копии (dry-run) до применения.
Правки в дереве поверх скриптов фиксируются отдельным выравнивающим патчем.
4.4. МАНИФЕСТ ВЫДАЧ. Ведётся один сводный манифест выданного (куда, что,
размер, контрольная сумма, дата). Перед каждой загрузкой — мгновенная проверка
«есть ли дубль», без перебора папок. Манифест также служит точкой входа при
возврате к замороженному проекту.
4.5. РОТАЦИЯ АРТЕФАКТОВ. Хранятся: текущая серия прогонов + 1–2 предыдущие.
Всё старше — регенерируется из базовых артефактов (эталон + конвертор/сборщик),
а не хранится. Патчи после применения сносятся (итог — в full_code/PSR).
4.6. ВЫДАЧА СЖАТО. Между спринтами — максимум один общий код-тхт; полные
комплекты (zip + full_code + PSR) — только на конечных точках. Крупные файлы —
сразу на внешний диск, минуя промежуточные копии.

## 5.5. Планирование ходов

5.1. РАЗВЕДКА БАТЧАМИ. Независимые чтения/поиски объединяются в один ход;
последовательность — только при реальной зависимости.
5.2. ИНКРЕМЕНТАЛЬНЫЕ СБОРКИ. Пересборка только изменённого; полный rebuild —
на контрольных точках.
5.3. ТЯЖЁЛЫЕ СБОРКИ — ПОСЛЕ КАРТОЧЕК. Планировать выдачу файлов так, чтобы
нужные карточки уходили до операций, обнуляющих квоту выдачи (сборки/установки).
5.4. ТОЧКА ВХОДА ПРОЕКТА. Для каждого проекта держится один файл «start_here»:
контекст, последний статус, что делать дальше. Вход в проект после любого
перерыва — за один ход, без перевспоминания истории.
5.5. ОДИН СРЕЗ ИСТИНЫ. Сводные статусы и журналы ведутся в одном месте и
дублируются в чат по запросу; версии в срезах — только актуальные.

## 5.6. Приоритет и разрешение конфликтов

6.1. КП1–КП4 приоритетнее КП5 в вопросах СООТВЕТСТВИЯ результата (состав
выдачи, формат документов, приёмки). КП5 управляет СПОСОБОМ достижения
(порядок действий, объёмы прогонов, места хранения).
6.2. При конфликте «экономия ↔ надёжность» на контрольной точке — побеждает
надёжность: полный пакет, полная сверка, полная выдача.
6.3. Экономия не должна менять смысл результата: если сомнение — переспросить
или расширить проверку, а не молча сократить.
