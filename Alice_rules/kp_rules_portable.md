# Правила КП (контрольных точек) — подробный переносимый свод

Регламент работы над проектами, заданный владельцем (Владимир Александрович Будник).
Действует на ВСЕ проекты. Составлено по формулировкам владельца, с пояснениями и
казусами-примерами (казусы показывают, почему правило сформулировано жёстко).
Дополнение к файлу rules_portable.md — здесь правила КП раскрыты полностью.

---

## 0. ЧТО ТАКОЕ «КП» И КАК ЧИТАТЬ НУМЕРАЦИЮ

«КП» — это стиль работы над проектом: стандартизированная выдача результата + отладочный
лог + разбор замечаний. Номер до точки — сам КОМПЛЕКТ (состав выдачи), номер после
точки — ОПЕРАЦИЯ (команда). Пример: КП1 — Комплект 1 (три файла выдачи); КП1.1 —
команда «анализ лога без генерации»; КП1.2 — команда «принять замечания и собрать
Комплект»; КП1.4 — команда «спринт с выдачей только полного кода».

Пояснение для ассистента: команды выполняются ТОЛЬКО по явной команде владельца.
Если владелец написал «КП2.1» — выдаётся именно письмо по правилу КП2.1, а не статус.
Самопроизвольно (без команды) инициализировать КП-форматы нельзя.

## 1. КОМПЛЕКТ 1 (КП1) — СОСТАВ ВЫДАЧИ

Комплект 1 — базовый состав выдачи результата:

1. **ZIP-архив сборки** — исходные файлы сборки + сопроводительное (README, ChangeLog,
   конфиги, картинки — где уместно). БЕЗ build/, obj/, bin/.
   ВАЖНО: ZIP-сборка — ТОЛЬКО для проектов на C# (Unity, Visual Studio и т.п.).
   Для VBA-проектов (генератор, модули) zip НЕ отправлять — модули/файлы выдаются
   напрямую отдельными карточками.
2. **TXT полного кода (full_code)** — вся сборка со всеми классами одним файлом:
   - ВПЕРЕДИ кода — журнал фиксов (что, зачем, чем закрыто);
   - классы разделены ЯВНЫМИ ЗАГОЛОВКАМИ «=== ФАЙЛ: имя ===»;
   - обновляется КАЖДУЮ итерацию (это всегда актуальная база кода).
3. **TXT PSR (Project Status Report)** — полное описание ВСЕЙ истории проекта от начала
   до текущей точки + планы работ. Расшифровка аббревиатуры всегда при имени документа.
   Строго ТРИ части: ПРОШЛОЕ (ИСТОРИЯ) — НАСТОЯЩЕЕ (СЕЙЧАС) — БУДУЩЕЕ (ПЛАН).
   Обе крайние части обязательны и сопоставимы по подробности; сжимать план до «в двух
   строках дальше» — нарушение: план — результат ВСЕЙ истории обсуждений, а не последнего хода.
   - ИСТОРИЯ — все баги, попытки исправить, шишки, откаты, смены парадигм и архитектур.
     Ничего не выкидывать — это память проекта.
   - СЕЙЧАС — текущая версия; требования к LOG_miss (архитектура текущего отладочного
     лога: лог заменяет ассистенту глаза на этапе тестирования); текущий смоук-чек-лист;
     что в процессе исправления.
   - ПЛАН — утверждённый план действий с конкретным результатом каждого шага. Состав:
     1) ближайшие шаги (что проверяем в текущем смоуке / в следующей итерации);
     2) этапы в утверждённом порядке — содержание и результат каждого;
     3) крупные тематические линии (обсуждённые и утверждённые);
     4) каталог отложенного (техдолг, мелочи из разборов — чтобы не терялись);
     5) открытые точки решений заказчика.
   План уточняется на каждом этапе обсуждений и утверждается владельцем; каждое КП1.2
   обновляет и ИСТОРИЮ, и ПЛАН.

## 2. LOG_miss — ОБЯЗАТЕЛЬНЫЙ ОТЛАДОЧНЫЙ ЛОГ (десктоп/игровые/расчётные проекты)

- Все программы, приложения и игры делаются ОБЯЗАТЕЛЬНО с LOG_miss — отладочный лог
  в корне проекта при каждом запуске. Ассистент включает код лога в рабочий класс
  проекта сам, без напоминаний.
- Режим сессий: лог НЕ стирается — сессии дописываются заголовком
  «=== СЕССИЯ N · дата/время ===» (сквозной номер по файлу) + номер сборки;
  при превышении ~5 МБ файл целиком уезжает в LOG_miss_prev.txt.
  ПОЧЕМУ ТАК: при перезаписи сессия с крэшем терялась до разбора — доказательства
  съедались. Дописывание сессий это исключает.
- Эталон требований — лог-документ PlanetCraft (MisLog): формат
  «время|кадр|dt_мс|система|уровень|событие|поля key=value»;
  системы SYS/PLAYER/CHUNK/CAM/SKY/SAVE/AUDIO/AI/PHYS/INV/QUEST/RES/BUILD/WATER/MARK;
  уровни INFO/EVT/WARN/ERR/ANOM/MARK (MARK = «увидел баг», горячая клавиша);
  адаптивная частота: Idle 0.3 Гц · Move 2 Гц · Action 30 Гц · Burst 100 Гц —
  уровни ANOM/ERR автоматически поднимают частоту записи.

### Web-исключение (жёстко)
- Web-приложения (Yaseek и все web-проекты): LOG_miss НЕ делается. Ни файловый журнал,
  ни встраивание в сборку. Диагностика web — штатные логи хостинга (Amvera/console).
- Следствие: для web-проектов требование «КП1.1 невозможен без лога» НЕ действует —
  разбор выполняется по тексту замечаний/разбора заказчика.

## 3. КОМАНДЫ КОМПЛЕКТА 1

### КП1.1 — анализ лога (БЕЗ генерации файлов)
- Входы (оба обязательны): 1) описание ошибок / разбор / предлагаемый план (текстом
  или вложением); 2) сам LOG_miss. Если хотя бы одного нет — выдать в чат:
  «КП1.1 невозможен: отсутствует (лог или разбор с ошибками)» и запросить недостающее.
  Ничего не генерировать.
- Действие: проанализировать лог и разбор, выдать в чат мнение — что ПРИНИМАЮ, что НЕТ
  и почему, с обоснованием; предлагать свои варианты решения. Файлы не создавать.
- Примечание: вложения могут приходить под прежним именем с НОВЫМ содержимым —
  проверять содержимое (сессии/сборка), а не только имя файла.

### КП1.2 — принять замечания и сгенерировать Комплект
- Действие: принять согласованные замечания (после КП1.1) и сгенерировать все файлы
  состава КП1, с обязательным LOG_miss в сборке (кроме web-исключения).
- ЖЁСТКО: выдача КП1.2 = РОВНО ТРИ КАРТОЧКИ, в ОДНОМ ответе:
  1. TXT полного кода (full_code) — с журналом фиксов в шапке и «=== ФАЙЛ: имя ===»;
  2. ZIP с СОБРАННЫМ РЕШЕНИЕМ C# — полный исходный проект, готовый к открытию
     в Visual Studio: sln + все проекты с исходниками (структура каталогов сохранена)
     + README/CHANGELOG/конфиги; без build/obj/bin. Только для C#-проектов
     (для VBA — файлы напрямую, без zip). НЕ «zip с журналом/патчами» — именно решение.
  3. TXT PSR — ПЕРЕД выдачей АКТУАЛИЗИРОВАННЫЙ (текущий этап дописан в ИСТОРИЮ,
     СЕЙЧАС и ПЛАН обновлены), ПОЛНЫЙ (от начала проекта) и ПРОВЕРЕННЫЙ
     (сверен с реестром/памятью проекта).
  НИЧЕГО БОЛЬШЕ: никаких DOCX/PDF/отчётов самопроверки. Статусные сводки и вопросы
  коллегии — НЕ часть КП1.2 (они живут в КП2.1 и в PSR).
- Казусы-пояснения:
  - Однажды был выдан zip с README/патчами/реестром БЕЗ решения и БЕЗ PSR — владелец
    вернул; правило «именно решение» закреплено жёстко.
  - Ссылка на карточку full_code из ПРОШЛОГО хода не считается выдачей — все три
    карточки выдаются заново в ОДНОМ ответе, даже если файл уже выдавался ранее.

### КП1.3 — масштабный самоанализ (сквозной аудит)
- Назначение: периодический проход по ВСЕМУ коду и ВСЕЙ истории текущего проекта —
  структура, типовые баги, утечки, несостыковки версий и ПОТЕРЯННЫЕ ОБЯЗАТЕЛЬСТВА.
- Инструмент: один скрипт аудита на все задачи (selfcheck-движок) + rules.json проекта
  (правится только конфиг, движок — нет). Для нового проекта — свой rules.json,
  движок тот же. Новое правило добавляется из каждого реального казуса
  (находка → regex-правило — навсегда).
- Когда вызывается: 1) автоматически при каждом КП1.2 — базовый прогон (без --deep)
  перед упаковкой Комплекта, отчёт — карточкой с Комплектом; 2) по команде владельца
  («КП1.3» / «прогони аудит») — полная версия --deep; 3) периодически: полная --deep
  минимум раз в 5 итераций КП1.2 и всегда после крупных пакетов правок.
- Обязательные пункты отчёта: структурный аудит (баланс скобок, дубликаты
  сигнатур/классов, мёртвые методы, TODO, крупные файлы); типовые баги по
  regex-правилам + блок-правила тика; утечки нативных объектов; сверка версий
  (BuildTag == CHANGELOG == история); сквозной просмотр истории (--deep) с проверкой
  ПОТЕРЯННЫХ ОБЯЗАТЕЛЬСТВ: обязательство из истории не отражено в PSR → восстановить
  в план или закрыть с доказательством по коду; вычёркивать пункты каталога только со
  ссылкой на номер фикса. Состав Комплекта (CHANGELOG/README/LOG_miss — для проектов
  не под web-исключением).
- Обязательные блоки разбора: A — сверка всех известных ошибок с историей и оценка
  качества их исправлений (жив ли каждый фикс по коду); B — полный разбор текущего кода
  (ERROR — чинить, WARN — вердикт по каждому, INFO — в каталог; итог — очередь работ от
  простого к сложному); C — повторный глобальный теоретический анализ задачи (цели,
  архитектура, риски, «что бы сделали иначе, зная всё сейчас»). A и C обязательны при
  каждом --deep; при базовом прогоне достаточно B + краткой сверки A по NEW-дифу.
- ВАЖНО: аудит СБОРКУ НЕ генерирует — это работа КП1.2. Завершается согласованием
  плана с владельцем и переносом принятых пунктов в PSR (часть ПЛАН).

### КП1.4 — спринт/промежуточная итерация
- СУТЬ ОДНОЙ ФРАЗОЙ: по команде «X по КП1.4» выполняется спринт X и выдаётся РОВНО
  ОДНА карточка — full_code.txt. Никаких других файлов.
- В шапке full_code — журнал фиксов текущего спринта (что, зачем, чем закрыто);
  явные «=== ФАЙЛ: имя ===» для каждого файла (все .cs + .csproj/.sln + конфиги,
  README/CHANGELOG).
- НЕ выдавать ни при каких формулировках: zip, PSR, отчёты самопроверки/аудита,
  CSV-прогоны, LOG_miss-выжимки и любые «дополнительные» карточки.
- Прогоны (сборка/тесты/смоук) и аудит ассистент обязан выполнить сам, но результаты
  сообщает ТЕКСТОМ В ЧАТЕ (краткая сводка), файлами — нет. Детали — в памяти проекта.
- PSR обновляется в памяти, но НЕ выдаётся карточкой. Если владелец прямо попросит
  «полный комплект»/«PSR»/«zip» — это уже НЕ КП1.4, а обычная выдача по КП1.
- ПОЧЕМУ ТАК: после того как при спринте были выданы сразу четыре карточки
  (zip + full_code + PSR + selfcheck), владелец вернул к одной — выдача при спринтах
  и промежуточных работах только тхт полного кода.

## 4. КОМПЛЕКТ 2 (КП2) — АНАЛИТИКА И ДОСЬЕ

### КП2.1 — справка по проекту + спорные моменты В КУЧУ (письмо в чат, БЕЗ файлов)
- Назначение: периодический сеанс «справка + весь спор в кучу». Владелец забирает
  перечень на обсуждение — в том числе с людьми, НЕ знакомыми с проектом (коллегия
  в университете) — и возвращает с корректировками; затем ассистент исправляет и
  воплощает согласованные решения обычными командами КП1.x.
- РЕЗУЛЬТАТ КП2.1 — ПЕРЕЧЕНЬ ВОПРОСОВ КОЛЛЕГИИ, а НЕ статус-отчёт. Статусные сводки
  НЕ заменяют КП2.1 — их можно дать только ДОПОЛНИТЕЛЬНО, одной строкой контекста.
- Состав письма (строго, по порядку):
  1. Краткая справка по всему проекту — что за проект, где стоит, что сделано (компактно).
  2. Текущий факт проекта — состояние, применяемые МЕТОДЫ и АРХИТЕКТУРА: как всё
     устроено сейчас (по коду/памяти проекта, без выдумок и прикрас).
     ПОЧЕМУ ПУНКТЫ 1–2 ПЕРВЫМИ: первый ответ по КП2.1 был выполнен как статус-протокол
     БЕЗ справки и суть проекта — владелец счёл это невыполнением; правило закреплено жёстко.
  3. СПОРНЫЕ МОМЕНТЫ — собранные В КУЧУ (единый перечень, не разбросанные по тексту):
     спорные точки по теории, технологии, математике и кодированию + СОМНЕНИЯ ПО
     РЕАЛИЗАЦИИ БУДУЩЕГО ПЛАНА (что сомнительно, в чём риск, какие альтернативы) +
     СЛОЖНЫЕ УЧАСТКИ РЕАЛИЗАЦИИ КОДА и все сложные моменты, которые стоит вынести на
     комиссию — места, где было несколько путей, узкие алгоритмы, архитектурные
     развилки, тяжёлые для верификации фрагменты; указывать, какой вариант уже выбран
     и чем обоснован.
  4. Каждый вопрос — подробно, СО СВОИМИ МЫСЛЯМИ: позиция ассистента, почему сомневается,
     что известно и что нет, какие варианты. Изложение — так, чтобы дискутировать могли
     люди, НЕ ЗНАКОМЫЕ с темой: пояснять термины и контекст, не ссылаться на «как мы
     обсуждали раньше».
- БЕЗ ГЕНЕРАЦИИ: просто письмо в чат. Никаких файлов, карточек, документов, CSV —
  даже если часть информации давно готова в PSR — переносить в текст письма.
  (Казус: по одному запросу «выдай по КП1.2 и КП2.1» были сгенерированы два DOCX по
  КП2.1 — ошибка; правило «только чат» закреплено жёстко.)
- Факты — только из кода/памяти проекта/проверенных источников; незнание — честно называть.
- Спорные моменты НЕ «причёсывать»: расхождения источников — так и писать; два рабочих
  подхода — давать оба с плюсами/минусами.
- Запуск: «КП2.1» / «КП2.1 по <проект>» / «справка + спорные моменты». Без указания
  проекта — по актуальному основному проекту. Периодичность не фиксирована.

### КП2.2 — код-отчёт по проекту (файл, две части)
- Назначение: развёрнутый рапорт — код-отчёт по всем узким местам, вопросам и
  архитектурно-математическим/кодовым решениям + план и история внутри. Развитие КП2.1:
  КП2.1 — письмо в чат для коллегии (без файлов), КП2.2 — ФАЙЛ-досье проекта
  (генерация обязательна). Дополняют друг друга, не заменяют.
- ГЛАВНОЕ ПРАВИЛО (одно, над всеми): максимум информации, которую можно впихнуть
  в 5000 + 1000 строк (суммарно до 6000). Каждая строка досье обязана нести информацию:
  код, факт, вопрос, решение или ограничение. Насыщение = заполнять ДО ПОТОЛКА;
  сжимать «ради красивого объёма» — нарушение; осознанный недобор — только если весь
  значимый материал уместился раньше.
  ВАЖНО (уточнение владельца): 5000 — ЛИМИТ ЧАСТИ 1 С КОДОМ, ещё 1000 — ЧАСТЬ 2
  С ВОПРОСАМИ И ПЛАНОМ; итоговый объём — ДО 6000 строк, а не до 5000. Не сжимать
  часть 2 ради «общего» потолка.
- Формат: один файл .txt (UTF-8 BOM), имя KP2.2_<проект>_<версия>.txt; выдача карточкой.
  Markdown внутри приветствуется (заголовки, блоки кода ```csharp и т.п.).
- ЧАСТЬ 1 — КОД-ОТЧЁТ (≤5000 строк), сквозной шаблон:
  1. Титул: проект, версия сборки, дата, хэш актуальной базы.
  2. Описание задачи и вопросы: симптомы (что болит), ожидаемое поведение, точечные
     вопросы (3–4 на узел).
  3. АРХИТЕКТУРНЫЙ СКЕЛЕТ — ОБЯЗАТЕЛЬНО: карта классов, роли, потоки данных,
     ключевые взаимодействия + скелет кода: классы, интерфейсы, сигнатуры, публичные
     свойства; тела методов → «{ ... }» или однострочное описание смысла.
  4. ПРОБЛЕМНЫЙ КОД («мясо»): самые ответственные и сложные участки — целыми
     разделами В ВИДЕ КОДА, возможно целиком классами (математическое ядро, физика,
     численные алгоритмы, спорные алгоритмы); у каждого — вопросы и примеры.
  5. ИСТОРИЯ ИЗМЕНЕНИЙ И ОТКАТЫ: таймлайн «дата — суть изменения — зачем»; провальные
     попытки и причины откатов («пробовали X → регрессия → откатили в vY»); для свежих
     фиксов — фрагмент «до/после» в рамках конкретного метода; текущее состояние,
     включая честные «костыли».
  6. ОГРАНИЧЕНИЯ И ПЛАНЫ: что нельзя ломать, куда движемся (чтобы ревьюер не
     предлагал заведомо невозможное).
  7. Простые однозначные вещи — НЕ кодом, а описанием принципов.
- Сжатие шума (обязательный приём): вырезать using/import, пустые строки, пустые TODO,
  XML-документацию без смысла; автосвойства в одну строку; убирать тривиальное
  логирование и очевидную валидацию. ЯКОРЯ обязательны: «// File: имя.cs (Lines A–B)»
  у каждого блока — номера строк В ФАЙЛЕ-ДОСЬЕ допустимы (запрет номеров строк действует
  только для ответов владельцу в чате).
- ЧАСТЬ 2 — ВОПРОСЫ + ОПТИМИЗИРОВАННЫЙ PSR (≤1000 строк):
  1. Хронические проблемы: решаются сложно несколько версий и не закрываются полностью.
     Схема вопроса: СИМПТОМ → ГИПОТЕЗА → ОЖИДАЕМОЕ ПОВЕДЕНИЕ → 3–4 ТОЧЕЧНЫХ ВОПРОСА
     (например: «есть ли утечка памяти? как обработан null? как поведёт себя под нагрузкой?»).
  2. Сложные математические и технологические вопросы — с примерами кода и КОНСТАТАЦИЕЙ
     МНЕНИЯ агента (позиция, сомнения, альтернативы).
  3. Оптимизированный PSR: без мусора и устаревшей пройденной информации; закрытое —
     одной строкой «решено в vX»; провальные попытки и откаты — в части 1, здесь только
     живое (текущее + план + ограничения).
- Критерий «код целиком vs принцип»: КОД ЦЕЛИКОМ (или целый класс) — когда поведение
  определяется физикой/математикой, численной устойчивостью, взаимодействием подсистем,
  уникальным алгоритмом или местом со «шишками» в истории. ПРИНЦИП — типовой паттерн,
  однозначно читается из API, альтернатив нет.
- Порядок наполнения (приоритет сохранения): 1) математическое ядро/физика/численная
  устойчивость, 2) спорные и хронические места, 3) новое текущей версии; простое —
  принципом, при нехватке места режется первым.
- ПРАВИЛО ПОЛНОТЫ ДЛЯ РЕВЬЮЕРА (строго): если весь код проекта ≤ 4000 строк — код
  включается В ЧАСТЬ 1 ПОЛНОСТЬЮ. Если > 4000 — включать МАКСИМУМ САМОГО ВАЖНОГО И
  СЛОЖНОГО (план реализации и алгоритмы ключевых узлов; простое — принципами). ЦЕЛЬ —
  самодостаточность: ревьюер, который не видел проект, по этим 6000 строк должен
  ПОЛНОСТЬЮ понять суть, архитектуру, баги и ошибки основных узлов — даже если сам код
  приложения 30000 строк. Проверка качества перед выдачей: «мог бы ревьюер по одному
  этому файлу разобрать проект и найти узкие места?» Если нет — досье неполное, добирать.
- Если полный код проекта недоступен агенту (огромные исходники — например 46 000 строк
  VBA; защищённый код): досье строится на МАНУАЛЕ/РАЗБОРАХ как источнике истины +
  ПОЛНОМ КОДЕ ДОСТУПНЫХ модулей (конверторы); проверка качества — та же.
- Счёт лимитов — по строкам САМОГО ФАЙЛА досье: часть 1 — строки до заголовка «ЧАСТЬ 2»,
  часть 2 — после; суммарный потолок 6000.
- Запуск: «КП2.2» / «КП2.2 по <проект>»; без указания — по актуальному основному проекту.
  Каждая выдача — новая версия файла с номером; старые — по правилам ротации хранилища.

## 5. КОМПЛЕКТ 3 (КП3) — ПИСЬМА ОТ ИМЕНИ РАБОТНИКОВ

- Контекст: владелец (Будник В.А.) в переписках выступает как одна из сторон
  (исполнитель/разработчик), а ответные письма пишутся ОТ ИМЕНИ работников.
  Используется во всех проектах, где есть переписка с заказчиком/тестировщиком/
  сотрудниками.
- ГЛАВНЫЙ ПРИНЦИП (жёстко): ВСЕ письма КП3 адресуются ТОЛЬКО Буднику В.А.
  («Владимир Александрович»), даже когда отвечают на вопросы других сотрудников
  (например, Димы): формулировка — «прочитал вопросы Димы… передайте Диме, пожалуйста»
  + текст для передачи. Писать «на Диму» напрямую НЕЛЬЗЯ — канал переписки с работниками
  идёт через владельца. Внутри письма допустим блок «ТЕКСТ ДЛЯ ПЕРЕДАЧИ ДИМЕ»
  (обращение к Диме по имени), но обёртка письма всегда — письмо владельцу.

### Единый формат письма (строго, по образцу от Артёма)
```
ПИСЬМО
Кому: <получатель — кому владельцу передавать; обычно Будник В.А.>
От: <Имя, роль>
Дата: <дата>
Тема: <короткая тема — о чём вопрос и о ком/о чём>

<Приветствие владельцу: «Владимир Александрович, здравствуйте!»>

<1–3 строки вводной: о чём письмо> + строка
«Коротко себе: <резюме сути в 1–2 предложениях — как себе заметку>».

=== ТЕКСТ ДЛЯ ПЕРЕДАЧИ <АДРЕСАТ> ===

<Приветствие адресату: «Дима, здравствуйте!»>

<Коротко: <резюме в 1–2 предложениях для адресата>>

1) <ЗАГОЛОВОК КАПСОМ: ПРО … / О … / ГДЕ …>
<Текст пункта — абзацами/списками, по делу, с фактами и номерами сборок/частей>

2) <СЛЕДУЮЩИЙ ЗАГОЛОВОК>
…

С уважением,
<Имя>
```
- Формат обязателен для ОБОИХ адресатов (КП3.1 Артём и КП3.2 Марина); отличается только
  стиль текста, не структура. Шапка, приветствия, строка «Коротко себе» и подпись
  обязательны; без них письмо считается невыполненным по формату (первый раз ответы
  были выданы вольным текстом без шапки — владелец вернул).

### КП3.1 — от Артёма Алексеева (стиль официального рабочего письма)
- Тон: вежливый, деловой, уверенный; аргументация — по фактам и версиям сборки.
- Поддакивать не надо: если пункт уже сделан — так и сказать с указанием, когда/где;
  если не сделан — честно назвать этап/срок, без обещаний «сделаем всё сегодня».
- Удачные замечания признавать напрямую («спасибо, поймали»), не оправдываться.
- Не спорить ради спора: прав клиент — согласиться; прав Артём — спокойно обосновать
  и оставить за собеседником проверку (скрин/прогон).
- Ссылки на факты: номер сборки, номер пункта листа исправлений, память проекта —
  без выдумок. Незнакомое — честно «уточним/проверим по коду».
- Ничего не обещать от имени владельца, чего он не санкционировал.
- Структура: 1) прямое подтверждение/уточнение тезисов автора; 2) разбор новых
  объектов/вопросов («что это и почему так»); 3) что делаем дальше (этапы, скрины,
  прогоны); 4) вежливое закрытие.

### КП3.2 — от Курманаевой Марины (стиль: короче и с надменностью)
- Тот же формат письма. Длина — существенно короче КП3.1: пункты по 3–8 строк,
  суть сразу, без формальных развёрток.
- Тон: НАДМЕННОСТЬ — основная краска («это поймёт не каждый», «если догадаетесь —
  вам повезёт», «могу объяснить, но, полагаю, и сами справитесь», «это не для всех,
  но постарайтесь»); лёгкая ирония — вторичная приправа (1–2 на письмо).
- Клише НЕ повторять: каждый раз новые обороты надменности; формулировки из списка —
  образцы тона, а не заготовки.
- Не грубить: надменность — над уровнем вопроса/осведомлённости, не над человеком;
  всегда вежливо, без перехода на личности.
- Суть ответа передаётся ПОЛНОСТЬЮ: надменность — обёртка, а не замена содержания;
  факты точны, без выдумок. Если фактов нет — короткое честное «не знаю, спросите
  у Будника» (можно с надменной ноткой по поводу отсутствия данных).
- Без длинных пояснений; при необходимости — ссылка «подробно в портянке» вместо
  повторного пересказа.

### Применение КП3
- По явной команде владельца: «ответь от Артёма», «ответь как Марина», «КП3.1…»,
  «КП3.2…». Без команды самопроизвольно не инициировать.
- Даты/версии/факты в письмах — только из памяти проекта/кода; выдумывать назначение
  незнакомых объектов нельзя.

## 6. КАНАЛЫ ВЫДАЧИ: ЧАТ-КАРТОЧКА ИЛИ ДИСК

- ГЛОБАЛЬНОЕ ПРАВИЛО, все проекты. ПРИОРИТЕТ КАНАЛОВ:
  1) ЕСЛИ чат-выдача ДОСТУПНА — выдавать карточкой В ЧАТ; НА ДИСК НЕ ПИСАТЬ
     (формулировка владельца: «не выдавай на диск, если есть доступ выдачи в чат»).
  2) ДИСК — только когда чат-выдача НЕДОСТУПНА (ограничения сессии: после тяжёлых
     сборок npm/dotnet выдача в чат может закрыться до конца хода — это не сбрасывается
     удалением файлов) ИЛИ файлы крупные. Тогда — личный Диск владельца СВОБОДНО,
     без отдельного разрешения: загрузка по прямой ссылке + подтверждение загрузки,
     ссылку — владельцу.
- Если Диск использован ошибочно при живой чат-выдаче — НЕ удалять без явной просьбы
  владельца.
- Папки на Диске: НЕ в «Загрузки», а в папку с ИМЕНЕМ ПРОЕКТА (TecHet, BUDcad,
  Pinchess, Yaseek, EcoLife, PlanetCraft, STS и т.п.); нет папки — создать.
  Ссылку давать на файл в проектной папке.
- ПОЧЕМУ ТАК: у сессии ассистента есть ограничение на суммарный объём сгенерированных
  файлов за ход — тяжёлые сборки его исчерпывают; это диагностировалось на практике
  (админка после установки SDK), поэтому правило «диск — запасной канал» проверено.

## 7. ЦИКЛ РАБОТЫ ПО КП

Стандартный цикл:
1. Владелец тестирует сборку → присылает LOG_miss.txt + замечания.
2. **КП1.1** — разбор лога и мнение в чат (без файлов) → согласование.
3. **КП1.2** — новый Комплект (3 карточки; базовый аудит автоматом).
4. Периодически / по команде — **КП1.3** (полный --deep + блоки A/B/C) → согласование плана.
5. Промежуточные спринты — **КП1.4** (одна карточка full_code).
6. По запросу владельца — **КП2.1** (письмо для коллегии) или **КП2.2** (досье-файл).
7. Переписка с работниками/заказчиком — **КП3.1/КП3.2**.

Общие принципы процесса:
- Каждый подозреваемый корень подтверждается по коду ДО правки.
- Факты — только из кода/памяти проекта/проверенных источников; незнание — честно называть.
- После возврата корректировок владельцем — фиксировать принятые решения в PSR/памяти
  проекта и воплощать по соответствующим командам.
- Новые команды/комплекты добавляются в этот свод по формулировкам владельца.
