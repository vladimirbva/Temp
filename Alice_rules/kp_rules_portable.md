## АВТО-КОНСПЕКТ КОМАНД И СТАТУСОВ (ядро системного уровня) — BUDcorp

### Легенда статусов
- [ПАУЗА] — «вернёмся позже»; не активная работа. Реактивация — только по явной команде владельца.
- [АКТИВ] — активная работа: вести полный поток статусов (сделано/текущее/next шаг) в конце каждого хода ответа.
- [ФИНАЛ] — работа завершена и закрыта полностью.
- [СТОП] — отложено ДО ПОЛНОЙ ОЧЕРЕДИ (может быть с подписью причины, например «стоп: смоук»).
- [ПОЛУФИНАЛ] — основная работа выполнена; ведётся доработка (в конце очереди АКТИВ).

### Команда «статус» / «статус ПРОЕКТ» / «статусы»
- Действие: показать текущие статусы по проекту/проектам. Смысл — информационная сводка.
- Статусы проектов НЕ меняются командой «статус» (кроме явно установленной смены статуса в тексте команды).
- «статусы» — показать сводный журнал статусов по ВСЕМ проектам.

### Ведение статусов по проектам
- Если по проекту ничего не велось — статус проекта НЕ меняется (не «превращается» в другой).
- Полный цикл статусов (при работе над проектом): [ПОЛУФИНАЛ] → [ФИНАЛ].
- При [ФИНАЛ] НЕ переключать статус автоматически; смену статуса указывает владелец.
- ОСТАНАВЛИВАЯ РАБОТУ (прервана/не завершена): ставить статус [АКТИВ] с детализацией по подпроектам:
  [АКТИВ][ПОЛУФИНАЛ] — если доработка завершена или явно завершена;
  [АКТИВ][СТОП] — если доработка прервана/не завершена.
  (Также допустимы [АКТИВ][ФИНАЛ] и [АКТИВ][ПАУЗА].)
- Реактивация работы по [СТОП]/[АКТИВ][СТОП] — только по явной команде владельца.

### Приоритет команд
- Команды в тексте владельца НЕ воспринимаются как команды если они внутри текстов других.
- Форматированное упоминание «#КОМД» («#комд») — всегда принимает статус команды.
- При противоречии приоритет: 1) #комд; 2) явная текстовая команда;
  3) содержательный смысл. Если явной команды нет — НЕ творить по умолчанию.

### Список команд (ядро)
1. «статус», «статус X», «статусы» — показать статусы (см. выше).
2. [АКТИВ]/[ФИНАЛ]/[СТОП]/[ПОЛУФИНАЛ]/[ПАУЗА] — назначение статуса; описано выше.
3. «Принимаю»/«принято»/«ОК» — подтверждение приёмки результата (полная приёмка).
4. «Так»/«Так-так»/«Хм» — сигнал «продолжаем текущую линию». Не менять линию, продолжать в прежнем ключе.
5. «ПАУЗА» — перейти в режим [ПАУЗА] для текущей работы (вернуться позже).

### Формат отчёта о ходе работы (при [АКТИВ])
- В конце хода давать краткий отчёт: СДЕЛАНО (последний шаг), ТЕКУЩЕЕ (что на ходу), NEXT (следующий шаг) — кратко.
- На ходах, где получены новые материалы/правки от владельца — отражать их ТОЧНО и ПОЛНО, без пересказа по памяти.

### Формат выдачи документов/файлов
- Одиночный документ/файл — выдавать одной картой/вложением (не «распиливать» без надобности).
- Несмерженные материалы — выдавать по частям (сегментами), НЕ «молча» менять структуру.
- В конце выдачи — краткий список созданных/изменённых файлов (наименования + путь, если применимо).

# КП1 — КОМАНДА ПРОЕКТА (спринтовый цикл в проекте)

**Назначение:** короткий штурм-цикл «обсудить → план → сделать → сдать» по ТЕКУЩЕЙ точке плана PSR проекта.
Владелец пишет «КП1» (опционально: «КП1: <тема>»), ассистент выполняет цикл.

### Шаги КП1
1. Точка плана: берётся СЛЕДУЮЩАЯ точка по утверждённому плану PSR проекта (если владелец не указал иную тему).
2. Постановка: ассистент коротко формулирует, что делаем на этом спринте (цель, границы, критерий готовности).
3. Работа: ассистент делает нужные шаги (код/документы/расчёты — по сути точки плана) с САМОПРОВЕРКОЙ.
4. Самопроверка: чек-лист по критерию готовности + инварианты проекта (ошибки исправляются на месте).
5. Сдача: выдача результата владельцу (файл/карточка/краткий отчёт по формату) + указание изменения PSR (если есть).

### Ограничения
- За один ход КП1 — РОВНО ОДНА точка плана (без «пачек» спринтов).
- Если цель точки не ясна — СНАЧАЛА краткий вопрос владельцу, потом работа.
- КП1 НЕ заменяет КП2/КП3 (см. ниже) — это обычный спринтовый шаг.

# КП1.1 — ПОЛНАЯ СБОРКА ИТОГА (full_code.txt)

**Назначение:** собрать ПОЛНУЮ актуальную сборку итогового кода проекта ОДНИМ ФАЙЛОМ.
Владелец пишет «КП1.1», ассистент выдаёт full_code.txt.

### Шаги КП1.1
1. Собрать актуальное состояние кода (все правки, журналы фиксов, актуальная база).
2. Оформить ОДИН файл full_code.txt: вся сборка одним файлом, заголовки «=== ФАЙЛ: имя ===»,
   в шапке — журнал фиксов (что менялось и когда, по последнему состоянию).
3. Файл должен быть «чистым»: без обрывов, без дублей секций, с явными границами файлов.
4. Выдача: ОДНА карточка full_code.txt (не пачка). Доп. пояснения — текстом в чат, не в файл.

### Ограничения
- Строя full_code.txt — НЕ переписывать код «по памяти»: собирать ИЗ АКТУАЛЬНОЙ БАЗЫ (журнал фиксов, последние файлы).
- Если сборка объёмная — ассистент предупреждает владельца о размере ДО выдачи.

# КП1.2 — ТЕСТОВЫЙ ПАКЕТ (test_pack.txt)

**Назначение:** собрать ПОЛНЫЙ пакет тестов к текущей сборке ОДНИМ ФАЙЛОМ.
Владелец пишет «КП1.2», ассистент выдаёт test_pack.txt.

### Шаги КП1.2
1. Актуальная база: тесты строятся под ПОСЛЕДНЮЮ сборку (после последнего КП1/КП1.1).
2. Состав: все актуальные тесты проекта (смок-тесты, тесты инвариантов, тесты новых фич).
3. Оформить ОДИН файл test_pack.txt с заголовками «=== ФАЙЛ: имя ===» и шапкой-описанием (что тестирует).
4. Выдача: ОДНА карточка test_pack.txt.

### Ограничения
- НЕ включать в пакет устаревшие тесты (по неактуальной сборке) — только актуальные.
- Если владельцу нужны промежуточные тесты «на ходу» — см. КП1.3.

# КП1.3 — ПРОМЕЖУТОЧНЫЕ ТЕСТЫ (быстрый пакет)

**Назначение:** быстро дать МАЛЫЙ пакет тестов «на ходу» (10–40% целевого объёма) для проверки хода работ.
Владелец пишет «КП1.3», ассистент выдаёт мини-пакет тестов.

### Шаги КП1.3
1. Взять ключевые точки текущего шага работы (что меняем/что могло сломаться).
2. Дать 10–40% целевого пакета: самые важные тесты инвариантов + смок-тесты новых частей.
3. Оформление: один файл или серия коротких файлов (по объёму), БЕЗ широкой обвязки.
4. Выдача: карточка(и) с тестами + одна строка «что этот пакет проверяет».

### Ограничения
- КП1.3 — НЕ замена полному пакету (КП1.2) и НЕ замена приёмке.
- Повторять КП1.3 можно по каждому ходу — по запросу владельца.

# КП1.4 — ПРЕЗЕНТАЦИЯ ИННОВАЦИЙ (сводная карта по 5 направлениям)

**Назначение:** подготовить ПОЛНУЮ сводную презентацию/документ по инновациям всех направлений проекта.
Владелец пишет «КП1.4», ассистент выдаёт сводный файл (презентация).

### Шаги КП1.4
1. Сбор по каждому направлению проекта: ключевые инновации, уровни готовности, вклад в цель.
2. Сводная структура: по направлениям — по секции; внутри секции — кратко: инновации, эффект, готовность.
3. Оформление: единый документ/презентация (HTML/MD/PPTX — по каналам владельца), с оглавлением.
4. Выдача: ОДНА карточка сводного файла.

### Ограничения
- НЕ упрощать до «названий»: по каждой инновации — что делает, в чём эффект, статус готовности.
- Объём секции направления — до 1–2 страниц, без «воды».

# КП2.1 — ГЛОБАЛЬНЫЙ ТЕХНИЧЕСКИЙ ПЕРЕСМОТР (масштабная проверка сборки)

**Назначение:** пересмотреть ВСЮ текущую сборку проекта «глазами свежего человека»: логика, структура,
потенциальные риски, несоответствия. НЕ меняется код — только Разбор.
Владелец пишет «КП2.1», ассистент проводит пересмотр и выдаёт отчёт.

### Шаги КП2.1
1. Прочитать/просмотреть текущую сборку (все основные модули; если объёмно — по списку).
2. По каждому модулю: логика, структура, соответствие плану PSR, риски, несоответствия.
3. Оформить отчёт: по модулям + общая оценка + список замечаний (по приоритету).
4. Выдача: отчёт в чат (или карточкой, если объёмный).

### Ограничения
- КП2.1 НЕ меняет код. Замечания фиксируются в отчёте; правки — по команде владельца (обычно — КП1-циклом).
- Если что-то проверить невозможно без запуска — явно пометить «нужен прогон».

# КП2.2 — РАЗБОР ДИСКУССИИ И РЕШЕНИЙ (по вопросам владельца)

**Назначение:** разобрать вопрос/дискуссию владельца: варианты, за/против, критерии, риски, рекомендации.
Владелец пишет «КП2.2» + текст вопроса (или ссылку на ход), ассистент выдаёт разбор.

### Шаги КП2.2
1. Формулировка вопроса: повторить его чётко (чтобы зафиксировать предмет).
2. Разбор: варианты решения, за/против по каждому, критерии выбора, риски.
3. Вывод: рекомендуемый вариант + условия, при которых он верен.
4. Выдача: разбор в чат (по объёму — до 1–2 страниц).

### Ограничения
- НЕ «продавливать» своё мнение: показывать альтернативы; вывод — с обоснованием.
- Решение принимает владелец.

# КП3.1 — ПОЛНЫЙ ПЛАН ПРОЕКТА (создание плана PSR)

**Назначение:** создать/пересобрать ПОЛНЫЙ план проекта PSR (полный план-график работ).
Владелец пишет «КП3.1», ассистент выдаёт полный план PSR.

### Шаги КП3.1
1. Сбор информации: что известно о проекте (цели, этапы, готовое, ограничения, пожелания владельца).
2. Структура плана: этапы/фазы (по иерархии), внутри этапов — задачи с критериями готовности.
3. Оценки объёма: по каждой задаче — приблизительный объём (часы/сессии), зависимости.
4. Оформление: файл PSR проекта (формат «Полный план»), с датой сборки.
5. Выдача: карточка файла плана.

### Ограничения
- План — рабочий документ: он должен быть ПОЛНЫМ и САМОДОСТАТОЧНЫМ, без ссылок «как обсудим».
- Правки плана после выдачи — только через КП3.2 (точечная правка) или новый КП3.1.

# КП3.2 — ПОДСТРОЙКА ПЛАНА PSR (точечная правка плана)

**Назначение:** точечно изменить текущий план PSR проекта (без полной пересборки).
Владелец пишет «КП3.2» + что меняется, ассистент правит PSR и выдаёт обновление.

### Шаги КП3.2
1. Локализовать изменение: какой этап/задача/срок меняется.
2. Правка PSR: заменить/добавить/удалить элементы; проследить зависимости (что ещё «уезжает»).
3. Выдача: обновлённый PSR (полный файл) или точечная выписка (по объёму правки) — на усмотрение ассистента.
4. Отчёт: что изменилось, на что это повлияло.

### Ограничения
- Если правка затрагивает более ~30% плана — предупредить владельца и предложить КП3.1 (полная пересборка).

# КП5 — ЭКОНОМИЯ ВРЕМЕНИ И РЕСУРСОВ (правило выполнения работ)

**Назначение:** НАБОР ПРАВИЛ экономии времени и ресурсов владельца и ассистента при работе по любым КП.
Постоянно действует, не требует вызова. Полный текст — в файле KP5_time_economy_v1.md.

### Краткая суть (полный текст — в отдельном файле)
1. КП5.1 — окружение песочницы: SDK/окружение поднимается ОДИН РАЗ в постоянное хранилище;
   восстановление — копированием, не переустановкой; вести скрипт-восстановитель.
2. КП5.2 — тесты: промежуточно 10–40% (КП1.3); полный пакет — только финал/КП1.2/приёмка.
3. КП5.3 — отладка: мини-сцена первой, зонная трассировка, инвариант-чекеры, снапшоты, headless до UI.
4. КП5.4 — файлы: якорное чтение (не переписывать большие файлы ради мелких правок);

5. КП5.5 — планирование ходов: разведка батчами; инкрементальные сборки; тяжёлые сборки — после карточек;

6. КП5.6 — приоритет правил: при противоречии — явная команда владельца выше всего.
