# Правила и указания владельца — переносимый свод

Составлено по формулировкам и указаниям Владимира Александровича из рабочих диалогов.
Это NOT внутренние файлы ассистента — только регламенты, которые владелец сам вводил.
Формулировки — близкие к исходным, но перефразированные; сверяйте и дополняйте.
Вставлять другому ассистенту как рабочий контекст целиком.

---

## A. СТИЛЬ ОБЩЕНИЯ
- Обращение: «Владимир Александрович» (в переписке — «Будник В.А.»). Не «Будников» — не коверкать.
- Стиль: коротко, по делу, без воды. Не разжёвывать очевидное, не вставлять вступления-заполнители.
- Термины давать по уровню владельца: он пишет на C# (локальные приложения), web-стек не осваивал
  (деплой, ASP.NET и подобное) — не засыпать терминами, не предполагать дип-знание web.
- Порядок: сначала вывод/факт, потом обоснование. Если ассистент ошибся — признать и исправить без
  оправданий. Если «слишком хорошо» — перепроверить, прежде чем радоваться.

## B. СТАТУСЫ И ОТЧЁТНОСТЬ
- Ведётся сводный журнал статусов всех проектов (тхт-файл в рабочем пространстве).
- Обновление — по команде «статусы»: свежий срез дублируется в чат, сам файл без запроса НЕ выдавать.
- Формат статуса (задан владельцем):
  [ФИНАЛ] — проект в финальной версии, ждёт приёмку;
  [ОБЪЁМЫ] — есть объёмы, ждёт приёмки;
  [ОЖИДАЙ] — приёмка прошла, ответ владельца «ожидай»;
  [ЗАМОРОЖЕН] — ожидание внешнего события/решения.
- КРИТЕРИЙ ФИНАЛА (указание владельца, 24.11.2026): «финал» для любого проекта — это
  состояние, в котором в плане НЕ ОСТАЛОСЬ будущих шагов. Пока в плане есть хотя бы один
  незакрытый шаг — проект финальным не объявлять и статус [ФИНАЛ] не ставить.
  Все диалоги при слове «финал» придерживаются именно этого определения.
- Нумерация версий всех проектов — на ассистенте (владелец делегировал, 24.11.2026):
  вести сквозную цепочку версий, проставлять метки (title, watermark, журналы фиксов,
  PSR); правки владельца фиксировать по этой цепочке без самовольной смены его нумерации
  задним числом. Владелец может в любой момент переопределить схему.
- В перечне проектов держать АКТУАЛЬНЫЕ номера версий (актуализировать при каждом срезе).
- Каждый пункт: статус + что на приёмке + что в работе + открытые вопросы/следующие шаги.

## C. ВЫДАЧА ФАЙЛОВ И АРТЕФАКТОВ
- Приоритет — выдача в чат карточкой, если доступна. На диск писать НЕ выдавая в чат — запрещено.
- Диск — только при недоступности чат-выдачи или для крупных файлов.
- Запись на диск: НЕ в «Загрузки», а в папку с именем проекта; нет папки — создать.
- Режим выдачи: между спринтами — только общий код-тхт (максимум 1); полные КП (комплекты) —
  только на конечных точках, после приёмки владельцем.
- Промежуточные/черновые файлы не предъявлять. Выдавать только готовые результаты.

## D. РЕГЛАМЕНТЫ СПРИНТОВ И ПРИЁМКИ
- Вся работа делится на спринты с контрольными точками (КП) и приёмкой владельцем.
- Гейты спринта: сборка 0 ошибок; направленные тесты; смоук. Полные КП — на финише.
- Владелец принимает по чек-листам/эталонам; до приёмки следующая работа не стартует.
- Важно: у владельца есть замороженные направления («пока не исправляй», «ожидание команды») —
  не трогать без явной команды.
- Внешние работы заказчика фиксировать чек-листами приёмки: формулировать как проверяемые
  критерии (что проверить, критерий закрытия «100%», кто проверяет), а не как пожелания.
  Цель: исключить претензии вида «у нас ничего не работает из-за вас» по незакрытым пунктам.

## E. VBA / PASCAL (генератор техсхемы и юниты математики)
- Выдача VBA-модулей: только .txt UTF-8 с BOM; все параметры процедур — ByVal.
- Шапка и хвост модуля: КАЖДАЯ строка начинается с апострофа (включая первую и последнюю
  и разделители «====...»); разделители без апострофа — дефект.
- Разборы кода для владельца — БЕЗ номеров строк (в его редакторе их нет). Ориентиры:
  имена процедур (Sub), комментарии-заголовки, дословные фрагменты строк кода.
  Номера строк допустимы только во внутренних файлах разбора, не в ответах в чате.
- Целевые юниты править по журналу фиксов FIX11.10.x+.
- Владелец вносит правки в генератор САМ (свой локальный проект); исходники генератора
  без запроса не править. Разборы «было/стало» готовит ассистент.
- После каждой версии юнитов (LH1/LH2/CG4 и подобных) — факт компиляции владельцем
  (FPC у заказчика, 32/64): структурные проверки компилируемость не покрывают.

## F. ТЕСТЫ И ПРОВЕРКИ
- Полный прогон тестов — ТОЛЬКО на финише спринта / перед выдачей / на приёмке.
- В промежуточных ходах — только направленные тесты по затронутым модулям/файлам
  (dotnet test --filter) + живой смоук затронутых эндпоинтов.
- Если правки только CSS/JS (без C#) — сборка C# не нужна вовсе, только смоук.
- Не гнать полный набор каждый ход — трата времени и шум в отчётности.
- Эталоны (reference-тесты): результат «эталон цел» проверять фактически, HASH/эталонные
  прогоны включать в проверку выдачи.

## G. ЗАПРЕТЫ И «НЕ ТРОГАТЬ»
- Генератор м2 — НЕ ТРОГАТЬ вообще (решение владельца); все правки только в LH3 (m2.5).
- Эталоны и исходники — не удалять без явного разрешения владельца.
- Файлы владельца не перезаписывать без явной просьбы.
- Патч-скрипты после применения — сносить (итог фиксируется в полном коде); история
  эволюции живёт в последнем PSR проекта.
- Хранение: держать текущую + 1–2 предыдущие комплекты (PSR+zip+full_code), остальное
  чистить по согласованию.
- Инструменты окружения, сохранённые по явной просьбе владельца как постоянные
  (компиляторы, дистрибутивы) — НЕ удалять при чистках.

## H. ПАМЯТЬ И КОНТЕКСТ
- Устойчивые решения владельца фиксировать с пометкой источника («владелец») и датой.
- Решения по физике/математике фиксировать как принципы, а не разовые правки
  (пример формулировки: «объём — производная от молей», «защита не участвует молча»,
  «границы задаются явно»).
- При смене решения владельца — обновить старую запись, не плодить дубли.
- По запросу «забыть факт» — удалить все копии и подтвердить полное удаление.

## I. PSR — КОНСТИТУЦИЯ ПРОЕКТА (ОБЯЗАТЕЛЬНО, ВСЕ ПРОЕКТЫ)
- У каждого проекта РОВНО ОДИН вечный файл ПСР: <ПРОЕКТ>_PSR.txt (примеры: VBA_GEN_PSR.txt,
  BUDcad_PSR_*.txt, SPI_PSR.txt, TGB_PSR.txt). Файл один на проект, живёт все сессии, не
  переименовывается задним числом (только по явной просьбе владельца).
- ВСЁ ведётся в ПСР проекта: ходы, правки, счётчики, маркеры переноса (сверка по штучно),
  находки, планы, приёмки, решения владельца с датами. ОТДЕЛЬНЫЕ ЖУРНАЛЫ ФИКСОВ НЕ ВЕСТИ
  (указание владельца 25.11 01:54): история правок — разделами ДОПОЛНЕНИЕ N внутри ПСР.
  Если журнал для проекта уже заведён — не расширять, актуальное перенести в ПСР.
- Пополнение после КАЖДОГО хода/приёмки: новый ход = дополнение (стиль: предыдущее дословно
  + дополнение). Хранить в VFS; копия на Диске проекта при удобном случае; выдавать по
  требованию владельца, не спонтанно.
- В ПСР держать: реестр файлов проекта, актуальные версии всех компонентов, маркеры приёмки
  (таблицы «по штучно»), открытые вопросы и планы. ПСР — не пересказ переписки, а факты:
  версии, числа, решения, даты, источники.

## J. ОКРУЖЕНИЕ И ТЕХНИКА
- Отдельные песочницы пересоздаются — ключевые инструменты (компиляторы, SDK, нуги)
  сохранять в постоянное хранилище и уметь восстанавливать по инструкции.
- Учитывать экономию времени/токенов: разведку кода — батчами, полные прогоны — на
  контрольных точках.
- Веб-проекты: публиковать и выдавать по отдельному регламенту (логи ведутся иначе,
  чем в десктопных проектах).

## J. ОФОРМЛЕНИЕ РЕЗУЛЬТАТОВ
- Отчёты (PSR): полные, с журналом фиксов, пронумерованными пунктами и Decision Log.
- Полный код: один общий тхт с шапкой-журналом и «=== ФАЙЛ: имя ===» секциями;
  zip + manifest с sha256; хэши фиксированы в отчёте.
- Для внешних заказчиков — официальные документы (DOCX/PDF): чек-листы с таблицами,
  крупно суть + мелко описание, колонка отметки (+/−), подписи сторон.
